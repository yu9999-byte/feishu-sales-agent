# 商机状态判断与下一步行动建议 SDD

状态：`Implemented / Automated Green / UI pending / 2026-09-25`

关联路线：`P1-PROGRESS`。关联需求：`PRG-001..012`。

## 1. 用户目标

销售提交一次客户沟通后，销售跟进 Agent 不只整理记录，还要基于本人可见的客户、商机、
历史跟进和任务说明：这次发生了什么变化、还缺什么、有什么风险、下一步建议做什么。

用户看到的内容必须分为四层：

1. **事实依据**：本次沟通原文或可跳转的业务记录。
2. **Agent 判断**：进展变化、信息缺口和风险；每条判断引用事实依据。
3. **下一步建议**：行动、时间和建议原因；建议不是已经执行的事实。
4. **待确认动作**：销售可修改下一步和时间，确认后才保存跟进并创建所选本人任务。

## 2. 当前切片范围

- 在飞书文本跟进和 Web 草案生成时创建版本化的推进判断快照。
- 对比本次沟通与匹配商机、近期跟进和本人任务，识别有依据的状态变化。
- 识别客户/商机匹配、客户需求、预算、决策链、下一步行动和执行时间等信息缺口。
- 识别本次沟通风险、竞品、来源冲突和本人逾期任务。
- 将草案中的下一步和时间作为可编辑建议；编辑后重算判断和任务候选。
- 无唯一客户、业务来源不可用或关键建议没有证据时，明确显示信息不足，不猜测。

## 3. 非目标

- 本轮不实现“商机超过 7 天没有更新”等定时或事件触发器。
- 不自动修改商机阶段、金额、预计成交时间，不自动通知主管或发送客户消息。
- 不用 Mem0、模型记忆或不可定位的推断作为业务事实。
- 不把保存后的项目风险卡、保存前质量检查或推进判断合并成一个模糊分数。

## 4. 领域契约

每个草案版本保存一个 `FollowupProgressSnapshot`：

- `state`：`advanced`、`steady`、`needs_attention`、`at_risk` 或 `insufficient`。
- `headline`：面向销售的一句话结论。
- `facts`：带来源类型、原文/记录内容、记录 ID、URL 和来源版本的事实。
- `findings`：`change`、`gap`、`risk` 三类判断，每条保存引用的事实 ID。
- `recommendation`：可为空；包含建议动作、时间、原因、证据 ID和 `requiresConfirmation=true`。
- `warnings`：权限、来源失败和数据不完整的用户可理解说明。
- `assessedAt`：本次判断时间。

快照只允许引用当前租户、当前销售已授权读取的上下文。历史草案没有快照时仍可读取。

## 5. 状态与边界

- 无唯一客户或业务来源不可用：`insufficient`，不生成推进建议。
- 有可定位风险：`at_risk`；有缺口但无风险：`needs_attention`。
- 有新进展且无更高优先级风险/缺口：`advanced`；否则为 `steady`。
- 来源冲突必须同时保留双方记录，不静默选择较新值。
- `暂无下一步`、空动作或无当前沟通证据时不生成可执行建议或任务候选。
- 编辑只创建新草案版本；确认版本复制同一判断快照，重复确认不重复执行。

## 6. 展示要求

飞书卡片和 Web 草案均先展示推进判断，再展示可编辑的下一步和待办预览。界面必须使用
“事实依据”“Agent 判断”“建议下一步”“确认后执行”等用户语言，不能泄漏 Base 列名、
内部风险代码或模型推理过程。

## 7. 验收口径

- 自动化覆盖正常进展、信息缺口、风险、信息不足、来源冲突、部分来源失败、无建议和编辑重算。
- 确认前 Base、Task 和外部消息保持零写入。
- 单测、集成、类型、Lint、构建和差异检查通过后只能标为
  `Automated Green / UI pending`；真实飞书/Web 对账后才能标记 `UI Verified`。
