# 销售动作执行反馈与结果修订 SDD

状态：`Approved / Green verified / 2026-09-23`

关联决策：`D-026`。关联需求：`FUP-006`、`FUP-009`、`FUP-010`、
`FUP-011`、`TSK-002`、`OPS-002`。

## 1. 目标

修复销售点击整表确认后，原卡片长时间没有可见变化、完成后突然变成成功卡的体验。
销售必须能立即知道系统已经接单，并能在执行完成后查看、修订或恢复失败动作。

本切片遵守三个产品原则：

1. 过程可感知：确认后立即出现持久的“执行中，请等待”。
2. 动作可回退：确认前可取消；失败后可返回预填表单；成功后可发起修订。
3. 结果可编辑：修订更新原跟进和原待办，不创建重复业务记录。

## 2. 范围与非目标

### 2.1 本切片实现

- 一张表单一次提交，跟进字段和待办选择共同作为一个确认版本。
- 同一张飞书卡片完成 `待确认 -> 执行中 -> 成功/失败` 状态转换。
- 成功卡提供查看跟进、查看任务和编辑跟进入口。
- 失败卡保留已完成步骤，提供返回编辑和重试未完成步骤。
- 成功后的修订更新原 Base 跟进；已有飞书待办被选中时更新原任务。
- 重复回调、重复确认和失败重试继续保持幂等。

### 2.2 本切片不实现

- 不逐字段弹出确认，也不为每个外部步骤发送独立卡片。
- 不展示模型隐藏推理。
- 不在执行中删除已经写入的外部数据。
- 不把取消勾选已有待办解释为删除待办；它表示本次不更新该待办。
- 不实现任意历史版本回滚或跨记录合并。

## 3. 用户交互契约

### 3.1 待确认

卡片展示一个完整表单：AI 跟进正文、客户/联系人、沟通信息、下一步、时间、方式、
参与人和待办选择。主按钮只有一个：

- 有可执行待办：`确认保存并创建所示待办`
- 无可执行待办：`确认保存（不创建待办）`
- 修订已有结果：`确认更新跟进及待办`

不再同时展示“检查修改”和“确认保存”两个提交按钮。点击主按钮一次性提交整个表单；
服务端以本次表单值执行最终校验。校验失败只更新同一张表单并定位问题，不产生业务写入。

### 3.2 执行中

通过最终校验并原子获取执行权后，卡片回调立即返回：

```text
正在执行
已收到你的确认，正在保存跟进并处理待办，请稍候……
执行中，请等待；请勿重复提交。
```

执行中卡不保留提交按钮。飞书客户端在回调等待期间可显示原生按钮 loading；该动画只是
增强，不作为唯一反馈。回调完成后，服务端延迟持久 patch 同一消息为执行中卡，再启动
外部写入，避免异步终态被回调响应覆盖。

### 3.3 成功

同一张卡片更新为成功终态：

- 首次登记：`跟进登记成功`
- 修订已有结果：`跟进更新成功`
- 提供 Base 跟进链接；有任务时提供飞书任务链接。
- 提供 `编辑跟进`，点击后在同一张卡片打开当前结果的预填整表表单。

修订提交后更新原 Base 跟进记录。若原动作已有任务且本次仍选择任务，则更新原任务；
若原动作无任务但本次选择任务，则新建一条任务；若已有任务但取消选择，则保留原任务不变，
卡片必须明确说明本次不会删除它。

### 3.4 失败

同一张卡片显示失败或部分失败，并列出诚实结果。提供：

- `重试未完成步骤`：使用已保存进度继续，不重复已完成的首次创建步骤。
- `返回编辑`：用当前表单值和已完成外部标识创建新的待确认修订动作。

修订动作重试更新操作时允许重复调用幂等的 Base/Task 更新接口，不创建重复跟进或任务。

## 4. 状态机

```text
pendingConfirmation
  | confirm once + final validation
  v
executing
  | all writes complete       | no/partial write fails
  v                           v
succeeded                 failed / partialFailure
  | edit                      | edit
  v                           v
new pendingConfirmation revision action
```

- 每次编辑创建新的 `pendingActionId`，旧动作和审计保持不可变。
- 卡片消息 ID 从旧终态动作原子转移给新修订动作，保证同一张卡继续工作。
- 租户、操作者、聊天、卡片消息和动作状态都必须匹配。
- 执行中的重复点击返回当前状态，不重新获取执行权。

## 5. 数据与端口契约

`PendingActionPayload` 增加可选字段：

- `operationKind`: `create | update`，缺省按历史 `create` 处理。
- `revisionOfActionId`: 被修订动作 ID。
- `executionTarget`: 已有客户、商机、跟进、任务的 ID 和 URL。

端口增量：

- `ControlStore.movePendingCardMessage(...)`：单语句原子转移卡片消息归属。
- `SalesRecordsGateway.updateFollowup(...)`：更新指定 Base 跟进记录。
- `TaskGateway.updateTask(...)`：更新指定飞书任务标题、描述和截止时间。

不新增数据库列或迁移；上述修订信息保存在现有 JSON payload/result 中。

## 6. 回调与执行时序

```text
飞书回调
-> 校验租户/用户/卡片/版本
-> 重算整个表单并做最终校验
-> 原子 acquire：pendingConfirmation -> executing
-> 立即返回执行中卡
-> 回调响应完成后延迟 patch 执行中卡
-> 异步执行 Base/Task
-> 保存 succeeded/failed/partialFailure
-> patch 同一张卡为唯一终态
-> 原卡 patch 失败时才补发一张结果卡
```

外部执行不得在回调返回前启动，避免快速成功终态被稍后的回调执行中响应覆盖。
