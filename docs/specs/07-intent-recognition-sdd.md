# 意图识别模块 SDD

状态：`Implemented / 2026-09-23`  
范围：飞书销售 Agent 的文本消息意图路由  
关联决策：D-016、D-025、D-027、D-028

## 1. 目标

让销售可以用自然语言表达意图，由 LLM 结合当前消息和授权上下文判断用户想做什么；
代码只负责状态机、权限、确认门和工具副作用。意图识别不再依赖一组覆盖不完整的关键词
作为主路由。

典型表达包括：

- `帮我写跟进`
- `把刚才这段整理成跟进`
- `那就记录下来`
- `帮我分析这个客户的风险`
- `你可以帮我做什么`

这些表达不应因为措辞不同而进入不同流程。

## 2. 意图契约

分类器输出版本化 JSON：

```json
{
  "schemaVersion": "conversation-intent-v1",
  "intent": "followup_capture",
  "confidence": 0.92,
  "reply": ""
}
```

P0 意图集合：

| 意图 | 含义 | 进入工具/写入 |
| --- | --- | --- |
| `general_chat` | 问候、能力介绍、闲聊 | 否 |
| `sales_qa` | 通用销售方法问题 | 否 |
| `content_generate` | 生成邮件、话术等草稿 | 否 |
| `business_query` | 查询客户、商机、任务等业务数据 | P0 未接通时只诚实降级 |
| `followup_capture` | 生成跟进草案 | 仅进入确认卡，确认前不写入 |
| `followup_analyze` | 分析上一段沟通对商机的影响 | 否 |
| `task_operation` | 创建或处理任务 | P0 只允许确认卡内的本人任务 |
| `opportunity_operation` | 修改商机 | P0 不执行 |
| `project_diagnosis` | 项目风险和推进诊断 | P0 无业务查询时诚实降级 |
| `memory_save` | 保存销售本人明确批准的偏好 | 写入 Mem0 长期记忆端口；失败不影响当前对话 |
| `ambiguous` | 无法可靠判断 | 追问或保持当前会话 |

## 3. 分类输入

分类器接收以下经过租户、用户和聊天边界过滤的内容：

- 当前用户消息；
- 最近短期对话消息，默认最多 12 条；
- 当前活跃工作流状态，例如 `record_or_analyze` 或 `followup_collecting`；
- 活跃工作流的来源文本或结构化草案（仅限当前用户和当前聊天）。

分类器不得接收未经 ACL 过滤的全租户客户数据，也不得接收其他聊天的消息。

## 4. 分类规则与代码边界

### 4.1 LLM 主分类

系统提示词提供意图定义、正反例和上下文优先规则。自然语言分类由 LLM 完成，不能用
`帮我写`、`写跟进`等前缀作为唯一判断依据。

### 4.2 代码状态机

代码不接受模型的权限或写入声明，只接受经过 Schema 校验的意图建议：

1. `followup_capture` 进入跟进内容提取和预填确认卡；
2. `followup_analyze` 只生成分析文本；
3. `ambiguous` 保持当前澄清状态或自然追问；
4. 低置信、Schema 失败、模型异常时不得进入写入链；
5. Base 和 Task 只能由用户在确认卡点击确认后执行。

因此“AI 判断用户想做什么”和“代码决定是否允许执行”是两个不同职责。

### 4.3 运行时实现边界

迁移后的生产实现使用 LangChain.js structured output 生成本契约，并在 LangGraph
`classifyIntent` 节点中执行。工作流服务负责置信度、会话状态、租户、卡片确认和工具副作用；
它不能把模型输出直接当成工具调用。旧 `OpenaiConversationAssistant` 已从生产代码删除，当前
不存在新旧主路由双读双写。

## 5. 关键交互

```text
客户事实 → AI 判断为 ambiguous → 澄清记录/分析
       → 销售说“帮我写跟进”
       → AI 结合当前澄清会话判断 followup_capture
       → 复用客户事实 → 生成预填跟进表单
       → 销售确认 → 写入 Base / 创建已勾选任务
```

没有可复用上下文时，`followup_capture` 只打开空白录入表单，不猜测客户事实。

## 6. 异常和安全

- 不能把模型输出的客户 ID、租户 ID、权限或已执行结果当作事实；
- 跨聊天、跨用户、跨租户和过期工作流不能承接原文；
- 原始客户文本不进入普通日志，审计只记录意图、置信度、来源消息 ID 和结果类别；
- 模型失败时回复可见错误，不自动降级为跟进写入；
- 业务写入仍由现有幂等、确认、审计和重试链路负责。

## 7. TDD 验收

### Red 必须覆盖

1. “客户事实 → 帮我写跟进”必须被分类为 `followup_capture`，不重复询问；
2. “客户事实 → 那就记录下来”与“把刚才这段整理成跟进”同样承接原文；
3. “客户事实 → 只分析一下”分类为 `followup_analyze`，不生成草案；
4. 普通问答、邮件生成和问候不进入跟进提取器；
5. 模型输出低置信或非法 Schema 时不产生业务副作用；
6. 分类输入包含当前聊天的最近消息，但不包含其他租户、用户或聊天内容。
7. 消息即使包含“写跟进”等词，只要模型返回非 `followup_capture`，也不能打开表单或调用跟进提取器；
8. 模型高置信返回 `followup_capture` 时，不得再被关键词门拦截；没有上下文时打开空白表单。

### Green 验收

- 模型提示词包含正反例和上下文规则；
- 工作流不再用关键词作为主路由；显式前缀只在模型分类后提取正文；
- 精确回归覆盖截图中的真实表达；
- 全量 Agent 单元测试、类型检查和构建通过。当前 Agent 测试为 `150/150`；真实 GLM 已验证
  `ambiguous -> followup_capture`，真实飞书干净双轮复测仍是独立验收门。

### 7.1 框架迁移验收补充

- LangChain structured output 对非法 JSON、低置信和模型超时必须返回可见安全结果。
- LangGraph `thread_id` 只能承接同一租户、销售和聊天的上下文；恢复前重新校验动作版本和 TTL。
- 迁移后旧关键词门不能作为主路由，旧助手不能继续产生第二条回复或第二次结构化提取。
- `memory_save` 只接受销售明确批准的偏好，写入带租户/销售 ACL；同一 ACL 范围内的 Mem0 召回
  作为提示参考，不作为客户、商机或任务事实。
