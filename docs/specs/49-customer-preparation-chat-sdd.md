## 技术切片

Web 以独立 state/effect 请求 GET results/:id/delivery；结果快照和投递查询各自处理 loading/error。只在持久结果路由读取此状态，普通客户准备页面不请求。状态查询响应使用 CustomerPreparationDeliveryStatus 共享类型，传输使用 axiosForBackend、withCredentials 和 normalizeError。状态区刷新不得触发报告重算或任何写接口。

修订保护：preparation_sessions 新增 revision，初次保存为 1，每次成功保存加 1。结构化保存必须携带 expectedRevision（新建为 0）；条件更新与版本比较在数据库同一 UPSERT 内完成。冲突抛明确错误，不覆盖新状态，不自动复用旧模型结果重试。原文旧分支暂保留无版本保存兼容，不能宣称所有聊天消息已经具备冲突保护。

准备状态持久化切片：preparation_sessions 新增独立 preparation_context JSON，保存已验证条件与 turnCount（1～8）；原文累计上限 12000 字符。写入前和读取后均校验严格 schema。旧原文会话 context 为 null，不能伪称已完成提取。模型提取失败不调用保存，因此保留原条件。本切片不提供并发修订控制，后续接工作流前仍须补齐。

### 准备结果持久投递设计（2026-10-19）

产品/业务：结果与通知投递分开记录。创建结果时必须原子创建 pending 投递，保存原始聊天归属；只能向原聊天投递本人结果，不接受客户端替换收件人。旧结果不回填未知聊天或发送状态。

交互：pending 可恢复发送；dispatching 表示发送处理中，sent 表示已记录消息 ID。任何发送异常、发送成功但本地记录失败、发送进程中断均保守视为 unknown，不以新键重发。unknown 需要核查，不能展示为已成功或普通可重试失败。

技术：030 新建 preparation_result_deliveries，以 result_id 唯一并外键关联结果；complete 使用同一 SQL 写入结果及待投递记录。claim 按租户/本人/结果领取 pending，冻结首条 text 和 token；五分钟未完成的 dispatching 转 unknown，不能再次领取。finish 仅当前 token、dispatching 可写 sent/unknown，并原子写不含正文的审计。工作流从冻结内容发送，稳定结果键不变。
