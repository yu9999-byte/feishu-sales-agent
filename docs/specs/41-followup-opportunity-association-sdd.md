# 跟进与商机关联重构 SDD

状态：`Implemented / Automated Green / UI Verified`

日期：`2026-10-16`

关联决策：
[客户、商机、跟进关系决策问答](../decisions/2026-10-16-customer-opportunity-followup-model.md)

## 1. 背景与问题

当前执行链在每次确认跟进时都调用 `upsertOpportunity`。当 AI 没有抽取出明确商机名称时，
系统会自动创建“客户名 - 销售机会”，并把跟进强制关联到该商机。这个行为把“客户沟通”
错误等同于“发现商机”，会制造没有真实项目含义的商机，进一步污染风险提醒、日报、周报、
商机决策和漏斗分析。

本规格重建以下业务事实：

- 跟进必须关联客户。
- 跟进可以不关联商机。
- 一个客户可以有零到多个商机。
- 一个商机可以有多条跟进。
- 客户拜访、电话、会议等是跟进类型，不必然产生商机。
- 只有销售在确认卡上选择已有商机，或明确确认创建新商机，系统才建立商机关联。

## 2. 需求编号

| 编号 | 需求 |
| --- | --- |
| `FUP-012` | 跟进必须关联客户，但商机关联可为空。 |
| `FUP-013` | 确认卡必须在一张表单内提供“暂不关联、关联已有、创建新商机”选择。 |
| `FUP-014` | 未出现明确商机信息时，默认“暂不关联商机”，禁止生成占位商机。 |
| `FUP-015` | 明确商机名唯一匹配当前客户已有商机时，卡片可预选该商机，但仍以销售提交为确认。 |
| `FUP-016` | 明确商机名未匹配已有商机时，卡片可预选“创建新商机”，并清楚展示新商机名称。 |
| `FUP-017` | 选择已有商机必须来自当前跟进上下文中的授权候选，不能接受任意记录 ID。 |
| `FUP-018` | 创建新商机必须有非空名称；没有名称时阻止提交，不得回退为通用名称。 |
| `FUP-019` | 执行结果必须准确说明本次是未关联、关联已有还是创建新商机。 |
| `FUP-020` | 历史泛化商机先生成只读候选清单；未经逐条确认不得删除、合并或改写真实业务数据。 |

## 3. 领域模型

```text
Customer 1 ── 0..n Opportunity
Customer 1 ── 0..n Followup
Opportunity 0..1 ── 0..n Followup
Followup 1 ── 0..n Task
```

一次待确认跟进保存一个不可变的商机关联快照：

```ts
type FollowupOpportunityAssociation =
  | { mode: 'none' }
  | {
      mode: 'existing';
      opportunityRecordId: string;
      opportunityName: string;
      opportunityRecordUrl?: string;
    }
  | { mode: 'create'; opportunityName: string | null };
```

快照属于确认版本。`create` 在确认前允许名称为空，但提交确认时必须校验为非空。销售修改
商机关联方式或名称时必须产生新草案版本，旧卡不能覆盖新版本。

## 4. 默认决策规则

| AI 抽取结果与上下文 | 默认卡片选项 | 外部副作用 |
| --- | --- | --- |
| 没有明确商机名 | 暂不关联商机 | 只写客户和跟进 |
| 商机名唯一精确匹配当前客户已有商机 | 关联该已有商机 | 不创建商机，只写关联 |
| 有明确商机名，但没有精确匹配 | 创建新商机 | 销售提交后才创建 |
| 相似或多个候选，无法唯一确认 | 暂不关联商机 | 由销售在卡片选择，不猜测 |

AI 只负责提出默认值。最终业务动作来自销售一次性提交的完整表单。

## 5. 飞书交互契约

继续使用 Card 2.0 的单表单、一次提交，不逐字段确认。卡片分为四个视觉块：

1. 跟进正文与客户信息。
2. 商机关联：单选“暂不关联 / 已有商机 / 创建新商机”，并显示商机名称输入。
3. 待办内容与截止时间。
4. 唯一主按钮“保存跟进并创建待办”。

选择值只在点击提交时通过 `form_value` 一次性回传。执行中卡和成功卡必须避免笼统写
“客户、商机和跟进已写入”，而要按实际关联结果显示。

Card 2.0 对下拉默认值的回传不能作为业务事实来源。商机关联选择器的第一项固定为
`keep_current`，界面展示“保持当前处理：…”；销售不改选时沿用 payload 中已经确认的
`opportunityAssociation`，只有主动选择其他项才覆盖。这样既让默认处理可见，也避免未操作的
下拉在回调中丢失或改变 AI 当前判断。

## 6. 执行状态机

```text
确认版本
  -> upsert customer
  -> none: 跳过商机
     existing: 使用已确认 record id，禁止 upsert
     create: 以已确认名称 upsert opportunity
  -> create/update followup（opportunity link 可空）
  -> create/update task
  -> result card
```

每一步继续使用现有幂等键和进度持久化。部分失败重试必须从已成功步骤继续：

- 已创建新商机后跟进失败，重试复用 `result.opportunityRecordId`。
- 未关联商机时跟进失败，重试不能转而创建商机。
- 已有关联时重试不能调用 `upsertOpportunity`。
- 历史动作没有关联快照时默认按 `none` 处理；若执行结果已保存商机 ID，则只用于完成原动作。
- Pending Action 每次从 PostgreSQL 重新加载时，解析器必须无损保留
  `opportunityAssociation`；任何 schema 已接受但返回对象遗漏的字段都视为持久化契约缺陷。

## 7. Base 写入契约

- 客户关联字段始终写入。
- 商机关联字段在 `existing/create` 时写单一 record ID。
- `none` 时创建跟进不写商机关联字段；更新跟进时显式清空旧商机关联。
- 不再生成“客户名 - 销售机会”。
- 商机表的创建与更新仍使用现有租户字段映射、负责人和幂等规则。

## 8. 历史数据治理

名称以“ - 销售机会”结尾只能作为候选信号，不能证明该商机无效。第一阶段只读输出：

- 商机记录 ID、名称、客户、状态和负责人。
- 关联跟进数量与最近沟通时间。
- 是否存在金额、阶段、任务或明确项目名称等保留证据。
- 建议动作：保留、重命名、合并、关闭或待确认。

任何删除、合并、重命名、关闭和跟进改链均需销售逐条确认，并另建可回退执行规格。

## 9. 验收条件

- 没有商机名的跟进确认后，Base 不新增商机，跟进的商机关联为空，任务仍创建。
- 选择已有商机时不调用商机创建接口，跟进链接到所选记录。
- 选择新建商机时只创建一个有明确名称的商机，重复确认不重复创建。
- 伪造已有商机 record ID 在任何业务写入前被拒绝。
- 成功卡与执行中卡不再声称每次都会写商机。
- 旧文本、妙记、文档和 Web 跟进入口继续共用同一关联契约。
- 受影响单测、Agent 全量、PostgreSQL 集成、三套 TypeScript、Lint 和构建通过。
- 真实飞书 UI 分别验收未关联、已有商机、新建商机三条路径后，状态才可升级为
  `UI Verified`。
