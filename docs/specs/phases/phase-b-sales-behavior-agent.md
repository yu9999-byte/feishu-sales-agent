## 1. 交付目标与切片

Phase B 把现有 P0“机器人文本 -> 结构化提取 -> 确认 -> Base/任务”扩展为销售可日常使用的
跟进工作流。所有来源进入同一输入作业、草案版本、质检和确认状态机；页面和飞书卡片只是不同
交互面，不各自实现业务规则。
但机器人收到的任意文本不等于跟进来源：必须由 B0 对话入口识别明确记录意图，或用户主动
打开表单，才进入本工作流；普通聊天、方法问答、内容草稿和查询均走各自分支。

| 切片 | 可运行结果 |
| --- | --- |
| B0 对话入口 | 普通聊天与销售问答、明确跟进、歧义澄清、未接通查询诚实降级 |
| B1 表单与文本 | Web/卡片表单、机器人文本、专业正文、可编辑草案、确认写入 |
| B2 质检闭环 | 完整度、质量分、证据、风险、建议、编辑后再质检 |
| B3 语音 | 语音消息下载、转写、来源引用、失败恢复 |
| B4 妙记/会议 | 已授权妙记或会议纪要导入、说话人/时间证据 |
| B5 文档 | 已授权飞书文档导入、分段证据、超长内容处理 |
| B6 执行与推送 | 任务状态同步、提醒、本人/主管策略推送、幂等恢复 |
| B7 个人日报 | 使用已确认事实生成个人日报并保留快照 |

## 2. 用户流程

```text
选择来源或直接输入
-> 创建输入作业
-> 读取/转写/规范化来源
-> LLM 结构化提取与专业正文生成
-> 保存前内容质检 + AI 建议 + 本人待办候选预览
-> 原聊天展示可编辑草案和证据
-> 用户可在同一卡片点击检查修改，任务候选随版本重算但不执行
-> 用户点击确认保存，当前表单值完成最终检查后一次确认并直接执行
-> 原子获取执行权
-> 匹配/创建客户与商机、保存跟进和质检快照
-> 只创建已确认且可执行的飞书任务
-> 原聊天本人结果通知（含无任务/部分失败）
-> 结合历史做项目推进质检；命中新风险/关键变化时条件推送
-> 经租户策略、证据和权限检查后才向主管/协作者推送
-> 详情深链与审计
```

确认前不得写客户、商机、跟进或任务。任务候选在保存前抽取仅供预览，跟进保存成功后才
自动创建；一个确认动作明确授权所示两个写操作。保存失败时保留已经成功的步骤并按幂等键
重试，不重新生成或静默改变用户已确认版本。任务创建失败不能谎称整个动作成功，结果卡
列出已保存记录和待重试任务。

## 3. 交互规格

### 3.1 Web 页面

- `/followups/new`：选择“表单录入”或“粘贴沟通原文”；表单字段为客户、联系人、沟通方式、
  沟通时间、主题、沟通正文、下一步、截止时间、参与人。
- `/followups/:id/edit`：独立 Web 表单的生成正文、结构字段、质检分、风险、建议和字段级
  证据；支持编辑、重新检查、确认写入和取消。机器人输入不以该页为必经确认页；
  Web 输入也使用相同任务预览与一次确认契约。
- `/followups/:id`：已确认版本、原始来源引用、质检快照、写入结果、任务状态和版本历史。

三页都必须支持 loading、empty、error、forbidden、stale 和 partial；直接 URL 访问再次执行
服务端资源权限校验。

### 3.2 飞书机器人与卡片

机器人首页提供“写跟进”“从妙记导入”“从文档导入”“今日任务”入口。B1 的“写跟进”打开
卡片表单；明确跟进意图的文本消息继续使用现有多轮补充。用户从哪个机器人聊天提交，就在同一个聊天接收
草案、确认及结果。第一张草案卡展示正文、保存前可用状态、阻断项/建议、证据、下一步
三要素和待办预览，支持在卡内“编辑补充”“重新生成”“检查修改”“确认保存并创建所示待办”
“取消”。编辑生成新版本并更新原消息卡，不因每次修改发送新卡；Web 编辑只作为可选辅助。
无可执行待办时卡片明确显示原因，确认按钮为“确认保存（不创建待办）”。
内部事件名可为兼容保留 `quality.reviewed`，但不再把它作为用户可见的考试式质检。
默认卡不显示 0–100 分和等级，旧真实 UI 的 73/B 不作为新体验完成证据。

卡片表单采用 Card 2.0 根层 `form`。用户发送“写跟进”后，机器人向该私聊发送表单；
`input` 与 `picker_datetime` 必须有唯一 `name`，提交按钮设置
`form_action_type: submit`。飞书回调的 `action.tag=button`、`action.form_value`
携带字段，不能当作普通 `action.value` 确认按钮解析。服务端必须按卡片消息 ID、租户与提交人
核验表单归属，有限时效与幂等键；提交仅生成草案和质检，不直接写 Base/Task。生成可能超过
卡片响应窗口，因此先返回处理中卡片，异步完成后展示质检预览；失败保留可重试状态。

飞书卡片的“实时”指提交/点击检查后刷新同一卡片，不要求按键级质检；Web 表单可以在字段
变化时计算完整度并高亮跳转。客户、联系人、沟通方式、下一步逐项检查；客户身份或有效
正文缺失不能确认，其余未知值必须由销售显式说明并降低完整度分，不由 AI 猜测事实。
线上事项以方式代替物理地点。需求、预算、决策链不明时可保存明确的“未知”并提出建议，
不能因为客户未透露预算就伪造数字。

“检查修改”和“确认保存”是两个不同意图：前者只保存新版本并刷新卡片；
后者确认卡片当前表单值，服务端重算保存前检查后，若可保存就在当次操作中
原子获取执行权。不得仅因回调中字段与已保存版本不同，就要求销售再点一次确认。

执行完成后，原草案卡在原聊天就地更新为唯一“跟进登记成功”卡，并显示 Base、Task
每一步结果和真实链接，其中“查看跟进记录”指向本次创建或命中的 Base 跟进记录；
如创建任务，另显示“打开飞书任务”。该卡不再次要求确认；只有原卡 patch 失败时才补发。
条件项目
推进质检卡只在保存后有新可行动风险、关键变化或销售主动请求时发送；无历史数据则降级
显示“样本不足”。三种跟进卡并非每次固定发送三张。跨角色通知、任务提醒和日报卡按各自
事件发送，不混入一次跟进的确认门。

首个条件风险卡切片只处理本次**已确认原文中可定位**的明确负面/停止推进、竞品介入、
售前或产品支持请求，以及已逾期行动。每个标签必须附原文片段与建议；只有预算未知或
决策链未知不单独发卡。尚未读取完整历史时必须显示“样本不足，暂不生成项目健康度评分”，
不能用跟进质量分代替。该切片只回原销售聊天，跨角色扩散仍等待策略与资源权限切片。

### 3.3 受控深链

卡片详情 URL 必须包含服务端签名的短期 token，载荷只有 `tenantId`、资源类型、内部资源引用、
目标路径和过期时间。解析后先走飞书 OAuth，再按当前成员重新授权；签名不授予权限。token 过期、
篡改、跨租户或资源无权都返回同一安全页面。

## 4. 统一领域模型

### 4.1 输入作业 `followup_input_jobs`

```text
tenant_id, id, actor_member_id, source_type,
source_ref_hash, source_locator_encrypted?, source_metadata,
status, attempt, idempotency_key, error_code?, retryable,
created_at, updated_at, completed_at?
```

`source_type = card_form | text | voice | minutes | document`；状态为 `received | processing |
needs_input | pending_confirmation | completed | failed | cancelled`。来源原文不进入通用日志。

### 4.2 草案与版本

`followup_drafts` 保存作业当前指针；`followup_draft_versions` 只追加：

```text
tenant_id, draft_id, version, created_by, creation_kind,
source_text, generated_body, structured_fields, evidence,
quality_snapshot, llm_model, prompt_version, schema_version,
confirmed_at?, created_at
```

`creation_kind = generated | user_edit | regenerated | confirmed`。确认版本不可覆盖；新编辑产生新版本。

### 4.3 证据

每个事实字段使用：

```text
field, value, assertionKind(fact|suggestion),
sourceType, sourceRefHash, quote, startOffset?, endOffset?,
speaker?, occurredAt?, confidence
```

quote 必须能在规范化来源中定位；无法定位的内容只能标为 suggestion。任务建议可以是 suggestion，
客户已经承诺、预算、时间、决策人等事实不得无证据补造。

## 5. LLM 契约

### 5.1 输入

```text
tenantTimezone, sourceType, normalizedSource,
formFacts?, previousConfirmedFacts?, previousDraft?, userEdits?,
allowedCustomerCandidates?, now, schemaVersion, promptVersion
```

不得把当前用户无权读取的历史、其他租户样本、Secret 或内部权限诊断发送给模型。

### 5.2 输出 Schema `FollowupGenerationV2`

```text
generatedBody
customer { name, contact, communicationMethod, communicationAt, topic }
deal { opportunityName, amount, stage, decisionChain[], competitors[] }
conversation { needs[], objections[], agreements[], risks[], progress }
nextStep { description, dueAt, ownerHint, participants[] }
evidence[]
suggestions[]
```

服务端用 Zod 严格校验、拒绝未知顶层字段、检查证据 quote 属于来源并规范化时间和金额。结构错误
或证据不成立只进行一次即时重试；仍失败则作业进入可重试失败，不创建半成品记录。

## 6. 历史质检规则 v1（后台兼容，不再作为确认卡展示规格）

以下权重与等级仅记录已实现内部快照规则，方便旧版本读取/回归；不再要求每次保存前
对销售展示数字分。新保存前规则按 B0 规格区分写入阻断项、任务阻断项与非阻断补充建议；
预算和决策链未涉及不是“本次沟通质量差”的证据。后续若重新引入销售辅导评分，需单独
定义证据、解释、触发条件并重新确认。

总分为 0-100，由确定性规则计算，AI 只生成解释和修改建议：

| 分项 | 权重 | 满分条件 |
| --- | ---: | --- |
| 基础完整度 | 25 | 客户 8、联系人/角色 5、沟通时间/方式 4、主题 3、清晰正文 5 |
| 客户与商机事实 | 20 | 需求 6、异议/共识 4、金额或预算状态 4、阶段/进展 3、决策链 3 |
| 下一步可执行性 | 25 | 明确动作 8、截止时间 7、责任人 5、参与人/方式 5 |
| 证据一致性 | 20 | 关键事实有可定位证据 12、事实/建议区分 4、无冲突 4 |
| 表达质量 | 10 | 专业简洁 4、事实与判断分开 3、无敏感/夸大表述 3 |

缺少客户名或下一步动作时最高 59；证据包含不存在 quote 时本版本不可确认。等级：`A >= 85`、
`B 70..84`、`C 60..69`、`D < 60`。分数只作后台兼容诊断，不作为默认卡片或单一绩效结论。

本规则的下一步缺失上限适用于未说明原因的空值。销售明确声明“暂无下一步＋原因”时允许
保存真实跟进，但不能伪装为满分或创建任务；若本轮无需行动，质检解释为什么不生成待办。
下一步计划的时间、地点/方式、参与人不足以形成任务时要提示补充，不能让 LLM 编造。
项目健康度另由 Phase C 基于历史证据计算，不复用此跟进质量分冒充项目质检。

首批风险标签：`missing_next_step`、`missing_due_at`、`budget_unknown`、`decision_chain_unknown`、
`competitor_mentioned`、`negative_sentiment`、`customer_commitment_unverified`、`overdue_action`、
`support_requested`。其中竞品介入、明确负向信号、未验证客户承诺和支持请求需要显式证据。

## 7. API 与事件

### 7.1 API

- `POST /api/platform/followup-inputs`：创建表单/文本作业；请求不接受 tenantId/actorId。
- `GET /api/platform/followup-inputs/:id`：读取本人或权限范围内的状态。
- `PATCH /api/platform/followup-drafts/:id`：以 `expectedVersion` 创建用户编辑版本。
- `POST /api/platform/followup-drafts/:id/review`：重新质检当前版本。
- `POST /api/platform/followup-drafts/:id/regenerate`：基于原来源和用户约束重新生成。
- `POST /api/platform/followup-drafts/:id/confirm`：确认精确版本并进入现有幂等执行器。
- `POST /api/platform/followup-drafts/:id/cancel`：取消未确认作业。
- `GET /api/platform/followups/:id`：读取已确认跟进详情。

所有写 API 要求同源/CSRF 防护、可信 session、RBAC、乐观锁和幂等键。冲突返回 409，不覆盖
其他标签页的更新。

### 7.2 事件

```text
followup.input.received.v1
followup.source.normalized.v1
followup.draft.generated.v1
followup.quality.reviewed.v1
followup.version.confirmed.v1
followup.execution.completed.v1
followup.risk.notification.requested.v1
task.status.changed.v1
review.personal.generated.v1
```

事件使用平台统一信封；消费者幂等键为 `(tenantId,eventId,consumer)`。

## 8. 权限与通知

- 销售只能创建、编辑、确认自己的草案；主管/管理员默认不能代替销售确认。
- 主管可读取汇报范围内已确认记录和允许推送的证据摘要，不能读取销售尚未确认的草案。
- 普通完成结果只发本人。主管推送仅在租户策略启用且命中高风险/关键里程碑/支持请求时发生。
- 新需求默认仅给本人；售前/产品支持须销售确认对象。团队群里程碑须确认目标群；竞品
  提及给本人，市场/主管仅在策略启用、有证据且收件人有权时接收。
- 同一风险以 `(tenantId,followupId,riskType,evidenceHash,policyVersion)` 去重；等级或证据无变化不重发。
- 涉及他人的任务负责人变更必须具备 `task:assign` 对目标范围的权限并再次确认。
- AI 判断任务已完成/变更仅生成带证据的建议；销售确认前不得调用飞书任务状态更新。
- 到期前一天/当天/逾期提醒按租户时区、免打扰和去重窗口调度，任务状态变化后停止旧提醒。

## 9. 失败与恢复

| 失败 | 外部行为 | 恢复 |
| --- | --- | --- |
| 来源无权/不存在 | 统一不可读取，不泄露存在性 | 修复授权后手动重试 |
| 空内容 | needs_input | 补充内容后续跑 |
| 语音转写失败 | retryable failed | 保留消息引用，允许重试/改文字 |
| 文档超长 | 显示已截断范围或拒绝 | 用户选择范围，不静默丢段落 |
| LLM 429/5xx | 有限退避，显示处理中/失败 | 使用同一 idempotency key 重试 |
| Schema/证据失败 | 不允许确认 | 一次修复重试，仍失败转人工表单 |
| 编辑版本冲突 | 409 | 拉取新版本后合并，不覆盖 |
| Base/Task 部分失败 | 显示成功步骤 | 复用现有部分失败恢复，不重复写入 |
| 推送失败 | 不回滚业务写入 | 独立 outbox 重试并去重 |

## 10. TDD 与固定评测集

### B1 Red

- 表单和文本产生同一 `FollowupGenerationV2`，未经确认没有业务写入。
- 用户编辑生成新版本，旧版本可回读；错误 `expectedVersion` 返回冲突。
- 非本人不能读/改未确认草案；管理员不能代确认。
- 重复提交、确认和回调不重复创建副作用。

### B2 Red

- 冻结分项规则精确计分并解释每个扣分项。
- 缺客户/下一步触发 59 分上限；伪造 quote 版本不可确认。
- 编辑补充截止时间/责任人后分数按规则变化且留下两个快照。
- 风险标签必须有证据；同风险未变化不重复请求主管通知。
- 同一聊天的卡片表单提交/编辑后返回新质检版本和更新后的任务预览，旧版本点击确认被拒绝；
  Web 字段变化即时刷新完整度，飞书卡按“检查/提交”刷新，不重复发送编辑卡。
- 联系人/沟通方式/下一步缺失有字段提示；显式“暂无下一步＋原因”可以保存但无任务；
  缺客户或有效正文、无效证据不可确认。任务候选必须可追溯到最终版本。

### B3-B7 Red

- 语音、妙记、文档规范化为相同来源段落和证据定位。
- 越权来源、空内容、转写失败、超长和限流均进入可恢复状态。
- 任务状态事件、提醒和主管推送在重复投递下只执行一次。
- 一次确认只创建卡中选择且预览过的本人任务；跟进写入失败不建任务；Task 失败仅重试
  未完成步骤，原聊天结果卡明确显示已保存记录与失败任务。
- 主管/售前/市场/群消息在事实未确认、策略关闭、无证据或收件人无权时零发送；任务状态
