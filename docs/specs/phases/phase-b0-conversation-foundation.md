# Phase B0 对话入口与可用性反馈规格

状态：`Approved / 2026-09-22；实现与 UI 验收单列`。
关联需求：`SIA-000..000D`、`FUP-004..006`。决策见
[问答](../../decisions/2026-09-20-conversation-and-quality.md)。

## 1. 首切片范围

原飞书私聊文本先经意图路由。支持问候/能力介绍、一般销售方法问答、内容生成草稿、
明确记录跟进、歧义澄清和未接通业务查询的诚实降级。沿用现有跟进表单、提取、
卡片确认、Base/Task 幂等执行链。通用多轮记忆、实时 Base 查询、任务独立创建、
商机改动、项目主动诊断和 RAG 在后续切片实现，不得伪装为已接通。

## 2. 意图契约

| 意图 | 例子 | 首切片响应 | 外部副作用 |
| --- | --- | --- | --- |
| `general_chat` | “你好”“你能做什么” | 自然问候和准确能力说明 | 无 |
| `sales_qa` | “客户一直压价怎么办？” | 销售建议，明确不是企业内部事实 | 无 |
| `content_generate` | “写封催方案邮件” | 可编辑文字草稿，不发送邮件 | 无 |
| `business_query` | “北辰最近怎样？” | 查询未接通则明说暂不能读取，不捏造结果 | 无 |
| `followup_capture` | “把刚才内容记成跟进：……”或“帮我写跟进” | 结合短期上下文进入预填草案；无上下文打开表单 | 确认前无 |
| `followup_analyze` | “只分析一下刚才的沟通” | 分析上一段沟通，不生成草案 | 无 |
| `task_operation` / `opportunity_operation` | “提醒我”“改阶段” | 未接通时明确说明；不偷换成跟进 | 无 |
| `project_diagnosis` | “这单有什么风险？” | 未接通数据时说明不能判断具体客户 | 无 |
| `ambiguous` | “张总说预算下周批” | 澄清“记录跟进还是只分析？” | 无 |

首切片分类输出必须是版本化 JSON Schema，含 `intent`、`confidence`、`reply`，
Zod 验证；不得信任模型声明的租户、权限或工具执行结果。自然语言意图由 LLM 结合当前
聊天短期上下文判断，代码只负责状态、权限、确认门和工具副作用。模型结果低置信、冲突或
解析失败时保守澄清/可见失败，不调用提取器。外部消息只在 `tenantId + messageId` 抢占后
处理，审计仅记意图/结果，不记原始敏感文本。

当前跟进补充会话由租户、用户与聊天共同约束；跨聊天或显式切换意图不能合并原文。
本切片的目标运行时使用 LangGraph Postgres Checkpointer 保存同租户/用户/聊天的 thread 状态，
默认向模型提供最近 12 条；长期语义记忆由 Mem0 OSS 按 ACL、来源和删除策略提供，客户、商机、
跟进和任务仍以确认后的业务表为准。旧 `conversation_turns` 只保留作迁移回放和历史证据。

## 3. 保存前卡片契约

卡片最强焦点是 AI 对本次沟通的事实摘要和保存动作，而非质量分。显示：

- 必须确认：缺客户/有效正文、无来源证据的事实、待办必要字段；未补齐时不得执行对应副作用。
- 建议补充：联系人、沟通方式、预算、决策链等本次未知项，不因未涉及就标成销售失误；
  某些缺口可能影响任务预览，但不应阻止真实跟进保存。
- 待办预览明确标题、时间、方式/人及是否勾选；无可执行任务只保存跟进。

保留旧评分字段作为版本兼容与后台规则回归，不在飞书确认卡显示数字和字母等级。
“重新质检”文案改为“检查修改”。点击“检查修改”只形成新版本、
重算检查与待办候选，不写入业务系统；点击“确认保存”表示确认卡片当前表单值，
系统完成最后一次同步检查后直接执行；即使本次点击携带了编辑值，也不得退化成
“仅检查，再次确认”。两种操作都必须按租户、用户、卡片消息和草案版本校验。
确认成功后，原卡就地更新为唯一、不可操作的“跟进登记成功”卡，不再新增内容相同的结果卡；
该卡必须包含 Base 跟进记录的可点击链接，如创建了待办则另显示飞书任务链接。只有原卡更新
失败时才允许补发一张结果卡，并记录失败与补发审计。
项目诊断与销售辅导绝不复用此卡上的记录完整度作为健康分或绩效结论。

## 4. LLM、权限、异常和验收

- 分类/问答只能看到本条输入和被授权的本聊天短期上下文；不得把全租户数据带入提示词。
- 一般建议可基于通用方法，但不得声称查到了客户、商机、任务或企业知识。生成草稿不发送客户。
- 模型 429/5xx 有限重试；失败时一条诚实错误提示，不得降级为跟进抽取。
- 群聊、非文本和机器人消息仍按既有范围忽略，不能在群里误触发写入。
- 真实 UI 验收：问候、方法问答、邮件草稿、歧义陈述、明确跟进命令与既有两卡闭环；
  查询未接通时无伪结果。记录消息/卡片、Base/Task 无副作用或正确副作用和审计 trace。

## 5. TDD Red 场景

1. “你好”“客户压价怎么办”“写封邮件”“北辰最近怎样”均不调用跟进提取器，
   不创建 pending action、Base 记录或任务；回复意图相符。
2. “张总说预算下周批”只澄清，不默认记录；分类器误判为跟进也不能越过显式指令门。
3. “把刚才内容记成跟进：客户……”，以及“写跟进”入口继续进入既有确认链。
4. 租户/消息去重、跨用户草案、模型失败时零副作用；已开跟进补充态不吞显式换话题。
5. 草案卡不再包含 0–100 数字/A–D 等级，突出事实、阻断项/建议和待办预览；
   Web 旧快照可读，模型/质检内部回归保持一致。
6. 编辑字段后点击“确认保存”必须在同一次操作中获取执行权，
   完成 Base 写入并发送成功卡；点击“检查修改”仍只更新版本，不产生外部写入。
7. 成功结果保存 `followupRecordUrl`，结果卡显示“查看跟进记录”；
   卡片发送成功和失败均有审计，不记录客户原文。
8. 正常确认只更新原卡且不调用新增结果卡发送；原卡更新失败时恰好补发一张。
9. 裸客户事实的澄清使用自然的动作选择文案，不出现“不会直接写入”等内部策略表述。

Red/Green/真实 UI 证据应追加到本文件末尾，不能用单元测试代替飞书实际体验。

## 7. 2026-09-21 真实 UI 缺陷修订

首轮 B0 真实飞书私聊已覆盖问候、销售问答、内容草稿、未接通业务查询、歧义陈述和
明确跟进。前五类均正确保持零业务副作用；明确跟进成功生成新版“保存前检查”卡，且不再
显示数字评分或字母等级。本轮同时发现两个不得以回调临时响应掩盖的缺陷：

1. 点击“取消本次跟进”后，控制库和审计虽已进入 `cancelled`，原卡却恢复成可操作状态。
2. 文本中明确出现“今天上午通过飞书”，草案仍把沟通时间、沟通方式判为缺失，并向用户
   暴露 `communicationMethod` 等内部字段名。

### 7.1 修订后的结构化提取契约

文本跟进的版本化 `FollowupDraft` 增加以下可选、可空字段；旧记录没有这些字段时仍可读取：

| 字段 | 含义 | 规则 |
| --- | --- | --- |
| `communicationMethod` | 本次已发生沟通的方式 | 只从来源明确事实提取；不能用下一步方式臆推 |
| `communicationAt` | 本次已发生沟通的时间 | 相对时间结合 `now` 与 `Asia/Shanghai` 转为 ISO 8601；未知为 `null` |
| `topic` | 本次沟通主题 | 只概括来源已有事实；未知为 `null` |

文本直录没有人工表单时，以上字段必须映射到 `inputForm`，供保存前检查和卡片默认值复用；
表单显式值优先于模型值。`communicationMethod` 与 `nextActionChannel` 必须保持语义分离。
模型输入必须同时提供 UTC instant 与业务时区本地时间；相对时间输出必须带该业务时区的显式
UTC offset。`Asia/Shanghai` 输出使用 `+08:00`，不能把本地钟点直接标成 `Z`。

### 7.2 卡片与终态契约

- 卡片只消费结构化 `missingItems`，统一在表现层转换为中文并去重；任何内部字段名都不得
  出现在用户可见文案中。
- 取消操作先以租户、用户和动作状态原子落库，再用已持久化的 `cardMessageId` patch 原消息
  为不可操作的“已取消销售动作”。patch 必须延迟到卡片回调响应完成后执行，避免飞书用
  回调后的表单状态覆盖同步 patch；同步回调内容不能作为持久终态的唯一手段。
- patch 失败不能把已取消动作恢复为 pending，也不能产生 Base/Task 副作用；必须写失败审计
  以便重试或排查。
- 已取消动作上的重复取消是幂等自愈入口：不重复改变业务状态，但应再次延迟 patch 原消息。

### 7.3 本轮 TDD 与复验门禁

1. 先证明旧实现取消后没有调用消息 patch。
2. 先证明文本提取结果即使包含本次沟通上下文，也未映射到 `inputForm`，且卡片会泄漏内部
   字段名或生成重复建议。
3. Green 后跑定向测试、全量 Vitest、三套 TypeScript、ESLint、Agent/Web 构建。
4. 真实飞书复验必须使用新的测试标记：卡片不再误报沟通方式/时间，不出现内部字段名；
   点击取消后原卡持续显示不可操作终态；控制库为 `cancelled`，Base/Task 零副作用。

本节自动化与真实 UI 两道门均已通过，状态为 `Implemented / UI Verified`。

## 8. 2026-09-21 无回复与问答等待态修订

### 8.1 事故证据与边界

真实飞书私聊 14:35 的“你可以帮助我做什么”仅显示用户消息，无机器人回复。开发者后台
`im.message.receive_v1` 仍指向 `qyavyq…tunnelmole.net/webhooks/feishu/events`，本地
Agent 的 3100 端口返回 200，但隧道进程已退出、该公网入口返回 404。当前证据指向事件
未到达 Agent，而非该句被意图路由错误吞掉。临时隧道的失效不能用模型提示词修复；恢复
新公网回调后，必须以真实飞书消息验证事件抵达。旧消息不自动重放，也不得谎称已回复。

### 8.2 问答等待态与终态契约

- 仅普通聊天、销售问答、内容生成、未接通业务查询及歧义澄清进入此契约；明确跟进仍沿用
  原草案卡流程。租户、消息去重和显式记录指令门不变。
- 在等待 LLM 之前，向原聊天发送一条轻量文本“正在组织回答…”。模型成功后编辑这条
  文本为最终答复，不额外留下永久的“正在回答”消息；不展示模型隐藏推理、未经验证的

## 9. 2026-09-21 “记录还是分析”多轮承接修订

### 9.1 缺陷与根因

真实飞书截图显示：销售先发送一段完整客户沟通事实，Agent 询问“记录为跟进还是只分析”，
销售回答“写跟进呀”后，Agent 又重复同一个问题。第一轮只发送了澄清文本，没有持久化
“等待用户选择记录/分析”的短期状态；第二轮模型只看到“写跟进呀”，无法承接上一条原文。
此外，原文里的下一步截止时间 `2026-09-19 18:00` 在复测时已经过期，不得作为默认勾选的
可执行待办继续创建。

### 9.2 澄清会话契约

- 当模型把客户沟通事实路由为 `followup_capture`，或明确回复“记录还是分析”的
  `ambiguous` 澄清时，先保存短期澄清会话，再在同一聊天发出问题。会话保存租户、销售、
  聊天、原消息 ID、原文和 TTL；`draft = null` 表示尚未进入字段补充态。
- 同一租户、同一销售、同一聊天在 TTL 内回复“写跟进呀/记下来/对，记录/需要记录”，
  必须只用上一条原文生成跟进草案；不得把确认短句拼入提取输入，并保留原消息 ID。
- 回复“只分析/分析一下/不记录”时，关闭澄清会话，让问答模型分析上一条原文；不创建
  跟进草案、不写 Base、不创建任务。取消、超时、跨租户、跨用户、跨聊天均不得复用原文。
- 明显换话题时先关闭澄清会话，再进入普通意图路由。无有效会话时单独发送“写跟进呀”仍
  打开空白跟进表单，不能猜测不存在的上文。
- 审计只记录澄清打开/解决的意图、源消息 ID 和结果，不记录客户沟通原文。

### 9.3 AI 意图与短期记忆修订

本节覆盖原先“单轮普通聊天”和“确定性显式记录指令门”的旧口径。分类器现在接收当前消息、
同租户/同销售/同聊天的最近短期消息，以及当前工作流来源文本。`帮我写跟进`、`那就记录
下来`等自然表达由 LLM 判断为 `followup_capture`；`只分析一下`判断为
`followup_analyze`。代码仍然校验 Schema、置信度、租户/权限/状态，并在确认卡确认后才
执行 Base/Task。

短期消息以 `conversation_turns` 保存，消息有 TTL、角色和幂等键，最多向模型提供最近 12 条。
`agent_sessions` 继续保存当前跟进草案，不替代通用对话记忆。没有相关上文时才打开空白表单，
不能根据一句“帮我写跟进”臆造客户事实。

### 9.4 过期待办契约

- 跟进事实可照常保存；任务候选的有效性单独判断。

  可选择候选。
