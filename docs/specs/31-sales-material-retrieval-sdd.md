## 1. 产品目标

客户沟通内容准备 Agent 已经能根据本人客户、商机和跟进事实列出“需要准备什么材料”，但
尚不能交付真实资料。销售资料检索与推荐 Agent v1 在不扩大数据权限的前提下，从管理员明确
加入白名单的飞书文档或知识库节点中读取真实内容，把最匹配的资料推荐到沟通准备页。

推荐结果必须包含真实标题、类型、飞书链接、匹配原因、原文摘录、引用位置、资料版本和
适用边界。没有可信结果时明确显示“未找到可信材料”，继续保留原“材料待补充”项，不用生成
内容、测试桩或猜测链接冒充企业资料。

## 2. 用户入口和结果

- 复用 `/customers/:customerRecordId/communication` 和
  `GET /api/platform/customer-communications/:customerRecordId`，不增加第二个割裂入口。
- 页面在材料区展示检索状态、检索范围和真实推荐；每条推荐可打开原飞书资料核对。
- 每条推荐同时引用形成检索意图的客户、商机或跟进事实，不把资料内容冒充客户事实。
- v1 只读、只推荐；不发送、不收藏、不保存草稿、不建任务、不修改资料和业务记录。

## 3. 白名单配置

- 白名单属于租户集成配置，放在 `base_mapping.knowledge.sources`，未配置时功能安全降级。
- 每个来源必须有稳定 `id`、`sourceType`（`docx` 或 `wiki`）、真实 token、真实 HTTPS URL、
  适用边界、关键词和允许匹配的材料分类。
- `docx` 表示单篇飞书文档；`wiki` 表示单个知识库节点。v1 不递归扫描整个知识空间。
- 白名单只证明“管理员允许被检索”，不证明当前销售有权阅读。
- 配置解析失败或来源超出支持类型时不启动宽泛搜索，也不回退扫描企业云空间。

## 4. 双重访问门禁

资料必须同时满足以下条件才可进入排序：

1. 来源存在于当前租户白名单，且白名单 token、URL 和类型契约有效。
2. 机器人能只读获取来源元数据和正文。
3. 飞书 ACL 可证明当前销售可阅读：
   - 文档链接为租户可读/可编辑，或文档协作者直接包含当前销售 `open_id`；
   - 知识空间为公开，或空间成员直接包含当前销售 `open_id`。

群、部门、用户组、应用或知识空间协作者不能自动推导为“当前销售本人可见”；ACL 无法读取、
只有机器人自身权限、身份不一致或来源失效时均 fail closed。页面只显示统一的安全警告，不泄露
无权资料的标题、摘要、token 或链接。

## 5. 只读适配器

- `docx`：读取文档元数据与纯文本正文；版本使用飞书 `revision_id`。
- `wiki`：先解析节点，校验空间访问，再只读取节点映射的 `docx` 正文；版本优先使用节点
  `obj_edit_time`，缺失时使用文档 `revision_id`。
- v1 不读取 Sheet、Base、附件、旧版 Doc、Slides、Mindnote 或任意外部链接。
- 单来源失败不影响其他白名单来源；错误只形成受控 warning，不返回部分未验证内容。
- 适配器不得调用创建、更新、移动、复制、授权或发送类飞书接口。

## 6. 检索与排序

- 查询词只来自沟通材料需求的标题、用途、原因和已引用业务事实，以及管理员配置关键词。
- 先按允许分类过滤，再按标题、配置关键词、正文命中计算确定性分数；不调用模型自由补全。
- 只返回分数大于零的结果，按分数、标题和来源 ID 稳定排序；同一来源最多返回一次。
- 匹配原因必须列出真实命中的词；无命中词不得生成推荐理由。
- 原文摘录从真实正文命中位置截取，引用位置使用正文段落序号；不得改写成未出现的承诺。
- 每次最多推荐 3 条真实资料，其余未满足的材料需求继续显示“材料待补充”。

## 7. 状态契约

- `ready`：至少返回一条双门禁通过且有真实命中的资料。
- `not_configured`：租户没有有效白名单，显示“资料库尚未配置”。
- `no_trusted_match`：已检查有效来源，但没有通过权限与匹配门槛的结果，显示“未找到可信材料”。
- `partial`：至少一条可信推荐可用，同时部分白名单来源失效或无法核验。
- `unavailable`：配置存在，但全部来源读取或权限核验不可用。
- 检索降级不得把整体客户沟通方案从 `ready/partial` 改成虚假的资料成功状态。

## 8. 身份、权限和副作用

- 沿用有效飞书 Web 会话、active 成员、同租户集成和本人客户范围。
- 在原 `customer:read`、`opportunity:read`、`followup:read` 之外增加 `playbook:read`。
- 当前销售身份只能取自认证会话 `open_id`，禁止前端提交或白名单配置冒充。
- 不把文档正文写入数据库、日志、记忆或缓存；API 只返回本次匹配所需的短摘录。
- 不写 Base、Task、控制库或审计业务事件，不触发消息、邮件、机器人和调度器。

## 9. 验收标准

- `KNO-001`：租户集成只接受显式、结构化资料白名单，默认不配置且不扫描。
- `KNO-002`：Docx 和 Wiki 节点适配器只调用读取与权限查询 API。
- `KNO-003`：机器人可读但销售 ACL 不可证明时不返回任何资料元数据。
- `KNO-004`：真实推荐包含标题、类型、链接、理由、摘录、引用位置、版本和适用边界。
- `KNO-005`：排序确定、最多 3 条、来源去重，且每条有业务事实来源键。
- `KNO-006`：未配置、无可信匹配、部分失败、全部不可用和来源失效均有诚实状态。
- `KNO-007`：Controller 要求四项权限，身份、租户、成员和集成失败均 fail closed。
- `KNO-008`：原沟通内容、拜访攻略和其他 Agent 回归不退化，页面仍无发送/写回入口。
- `KNO-009`：专项、全量、Postgres、发布器、调度客户端、TypeScript、Lint、构建、迁移幂等、
  启动冒烟和 `git diff --check` 通过；真实 UI 按当前要求保持 pending。
