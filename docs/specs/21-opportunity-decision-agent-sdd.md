# 客户与商机决策 Agent v1 SDD

日期：2026-10-06  
状态：`Implemented / Automated Green / API and bot integrated / UI pending`

关联路线：`P1-PROGRESS / COP-001..007`。关联测试：
[客户与商机决策 Agent v1 TDD](22-opportunity-decision-agent-tdd.md)。

## 1. 产品目标

当销售询问“现在最该推进哪个客户或商机、为什么、下一步做什么”时，Agent 必须读取本人
当前可见的客户、商机、历史跟进和已确认任务证据，给出带依据的推进优先级和行动建议，
而不是让模型凭聊天上下文编造结论。

v1 同时服务两个入口：

- 飞书机器人中的业务查询或项目诊断，由 Agent 直接返回用户语言的决策摘要；
- 已登录 Web 调用 `GET /api/platform/opportunity-decisions`，获得可供后续页面使用的稳定结构化契约。

## 2. 用户可见结果

机器人回复固定回答五件事：

1. 现在最该推进哪个商机和关联客户；
2. 为什么排在最前，包括风险和信息缺口；
3. 建议的下一步是什么；
4. 最近一次可信跟进依据是什么；
5. 随后还应关注哪些商机或全局任务风险。

回复必须明确“建议尚未执行”。没有可靠数据时说明数据源不可用，不输出看似确定的业务结论；
没有进行中商机时说明已赢单、已丢单和已关闭商机不会进入推进排序。

## 3. 数据、身份与权限范围

- 只读取当前租户、当前活跃成员、当前销售本人负责的数据。
- Web 入口要求有效飞书登录和服务端 `opportunity:read` 权限；租户集成身份不一致时失败关闭。
- 机器人入口在读取前重新校验活跃成员、当前角色会话和 `opportunity:read`。
- Base 网关分别按负责人分页读取本人客户、商机和历史跟进，并保留客户—商机—跟进的显式
  record 关联、记录链接和来源版本。
- 某类表缺少负责人字段时不读取该类数据，不通过无范围查询补齐结果。
- 任务证据复用任务履约服务，但以 `readOnly=true` 执行，不保存任务状态快照或事件。
- 只有 Agent 已成功确认动作中的明确商机名和精确 `taskGuid` 才能关联任务承诺；普通飞书任务
  只形成全局风险，不按标题、日期或文本相似度猜测商机关联。

## 4. 确定性决策规则

### 4.1 进入排序的商机

只有生命周期为 `active` 或 `unknown` 的本人商机进入排序。`won`、`lost`、`closed` 均从推进
队列排除并单独计数；`unknown` 保留在队列中，同时产生“商机状态待确认”风险。

### 4.2 风险与缺口

v1 识别以下可证明风险：

- 商机下一步截止时间已逾期；
- Agent 已确认且精确关联的任务逾期或发生变化；
- 超过 14 天没有可信跟进，超过 30 天提升为高风险；
- 没有关联跟进证据，或有关联跟进但可信沟通时间缺失；
- 商机生命周期无法映射。

v1 识别以下信息缺口：关联客户、当前进展、预计金额、下一步行动、下一步时间缺失。
金额缺失只作为缺口，不填充虚构金额，也不计算赢单概率。

### 4.3 优先级与建议

健康等级依次为 `critical > at_risk > needs_attention > on_track`。同等级按确定性风险/缺口
分数降序，再按真实预计金额降序和商机名称稳定排序。逾期下一步或已确认任务逾期属于
`critical`；分数只用于排序，不向用户解释为成交概率或模型置信度。

建议优先处理精确任务逾期、商机下一步逾期、长期未跟进、跟进时间缺失和生命周期未知，
再补齐缺失业务信息。每条建议引用风险或缺口证据，且始终带
`requiresConfirmation=true`；v1 不执行建议。

## 5. 响应契约与降级

`OpportunityDecisionResponse` 返回检查日期、时区、状态、汇总、排序结果、全局任务提醒、
来源覆盖和 warning。状态为：

- `ready`：有排序结果且关键来源完整；
- `partial`：保留可证明结果，同时明确部分来源或任务证据不完整；
- `empty`：没有可供推进的本人进行中商机；
- `unavailable`：身份、日期/时区、商机来源或关键范围不可可靠使用。

来源覆盖分别说明客户、商机、跟进和 Agent 已确认任务证据。分页不完整必须显式 warning；
来源失败不能由模型记忆、普通聊天或其他租户数据补齐。

## 6. 副作用边界

本阶段只读：

- 不修改客户、商机、跟进或任务；
- 不创建任务，不保存任务观察快照；
- 不联系客户，不发送主动提醒，不通知主管；
- 不更新商机阶段、金额或预计成交时间；
- 不调用 S4 真实投递入口，不创建或启用 cron。

后续若把建议变为动作，必须继续使用“预览 -> 人工确认 -> 幂等执行 -> 结果回读与审计”边界。

## 7. 当前非目标

- 没有客户 360 或商机详情正式页面；Web 当前只提供结构化 API。
- 没有主管团队商机组合排序；v1 仅为销售本人范围。
- 不预测成交概率，不基于自由文本猜测生命周期，不生成财务预测。
- 不做真实飞书/Web UI 验收；自动化和启动冒烟不能替代 UI 证据。
- 不把商机停滞提醒的调度/投递能力解释为本决策 Agent 已主动执行建议。

## 8. 验收标准

- 风险更高的商机稳定排在前面，关闭类商机不进入推进队列。
- 每个风险、缺口和建议均可回到本人范围的明确证据。
- 无负责人范围、跨租户、无权限和来源失败均失败关闭。
- 普通任务标题不能形成商机关联；只有显式 Agent 确认证据可关联。
- 机器人 `business_query`、`project_diagnosis` 使用真实决策服务，不采用模型生成的无数据业务结论。
- 决策读取不会产生任务快照、业务记录或消息副作用。
- 单元测试、全量 Agent、Postgres 集成、三套 TypeScript、Lint、双构建、迁移幂等、启动冒烟和
  `git diff --check` 通过后，只能标记 `Automated Green / UI pending`。

## 9. 后续演进

下一阶段优先把同一决策契约接入客户 360 和商机详情页，让销售能查看完整证据、风险、缺口和
建议；随后再扩展主管团队商机组合决策。任何自动任务、商机更新或客户触达仍须单独设计确认、
权限、幂等、审计和失败恢复，不由本只读版本隐式放开。
