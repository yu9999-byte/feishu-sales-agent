## 2. 规格状态

每份规格使用以下状态，不允许跳级：

```text
Draft -> Approved -> Implementing -> Implemented -> UI Verified
```

- `Draft`：仍可调整，不允许据此宣称功能完成。
- `Approved`：用户可见规则已经确认，可以开始写失败测试。
- `Implementing`：至少有一个对应测试已经运行并按预期失败。
- `Implemented`：自动化测试、类型检查、Lint 和构建通过。
- `UI Verified`：真实飞书或真实 Web 页面按角色完成端到端验收，并记录证据。

## 3. SDD / TDD 门禁

每个可交付切片严格采用同一顺序：

1. 用稳定需求编号写清正常流、异常流、权限和验收条件。
2. 用户确认会影响体验或业务结果的规则。
3. 先写测试并实际运行，保存预期失败的测试名和失败原因。
4. 实现使测试通过的最小代码，不夹带下一阶段功能。
5. 重构后运行受影响测试与 P0 回归测试。
6. 在真实飞书和 Web UI 中验证，并把证据写回追踪矩阵。

如果测试一开始就通过，必须判断是已有行为已经覆盖，还是测试没有验证新需求；不能把没有
经历有效 Red 阶段的测试记录为 TDD 证据。

## 5. 当前基线

已验证且必须保持回归通过的 P0 能力：

- 飞书私聊文本触发结构化提取。
- 缺少客户、下一步或截止时间时对话追问。
- 消息卡片确认或取消。
- 确认后写入 Base 客户、商机、跟进并创建飞书任务。
- 事件和卡片幂等、部分失败续跑、审计及两租户代码级隔离。

尚未进入实现的 Goal v3 能力不得在文档或 UI 中标记为可用。

## 6. 基线确认记录

2026-09-19 用户回复“启动”。本项目据此确认 Goal v3 SDD 基线及以下默认业务规则，并进入
Phase A TDD：

1. 普通跟进不推送主管，仅高风险、关键里程碑或明确支持请求等事件推送。
2. 质量评分用于辅导，不自动作为绩效扣分依据。
3. 首版会议输入读取飞书妙记或会议纪要，不实现机器人实时入会录音。
4. 首版文档输入仅读取已授权飞书文档。
5. 预测数据不足时显示“样本不足”，不输出伪精确数值。
6. Base 继续作为客户、商机和跟进的首个业务事实源。

## 7. 2026-09-20 增量确认

用户确认：机器人输入必须在提交内容的原飞书聊天完成草案编辑、再质检、确认和结果反馈；
草案卡同时预览本人待办，一次确认后先保存跟进，再自动创建所示任务。普通流程通常为
“草案＋实时内容质检卡”和“执行结果＋任务卡”；只有新可行动项目风险、关键变化或主动
分析才发第三种项目推进质检卡。跨角色通知、报告和提醒按独立事件发送。

这个决定覆盖 Phase B 中把 Web 编辑页当作默认确认路径、把任务创建放在无预览确认之后、
以及 AI 先改任务状态再请销售追认的旧假设。P0 与 Web 的历史验收证据继续保留，但不能
证明新增飞书卡片体验已实现。

## 8. 2026-09-23 框架与记忆增量

用户确认采用 LangChain.js + LangGraph.js，并要求替换当前自研意图/记忆主路径。新的运行时
由 StateGraph 负责唯一对话编排，LangChain 负责模型适配和结构化输出；Postgres Checkpointer
负责短期 thread 状态和暂停恢复；Mem0 OSS 作为长期语义记忆框架，必须经过 ACL、来源、删除和
评测门禁。客户、商机、跟进和任务仍以 Base、飞书 Task 和控制库为事实源。

本决定覆盖 D-025 中“P0 不引入外部记忆框架”的范围，但不覆盖其中的 AI 优先意图、确认前零
副作用和租户/用户/聊天隔离原则。代码迁移遵循
[LangGraph Agent Runtime SDD](10-langgraph-agent-runtime-sdd.md)，先文档和 Red 测试，再替换
主路径；在完成下线前禁止新旧实现双读双写。
