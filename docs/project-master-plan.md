# 销售跟进执行 Agent 项目主计划

状态：`Approved / multi-agent sales assistant direction confirmed / updated 2026-10-04`

本文把产品总纲、当前代码实现、规格文件、测试证据和真实飞书验收记录统一为后续推进基线。
它定义产品方向和阶段顺序；具体接口、状态机和字段契约仍以 `docs/specs/` 与
`docs/decisions/` 为准。

## 1. 产品定义

项目暂定名称为 **多 Agent 销售助手**，首个核心场景为 **销售跟进 Agent**。产品服务 ToB 一线销售，目标不是单纯生成一段
跟进文字，而是把一次客户沟通推进到可确认、可执行、可追踪的业务闭环：

```text
理解沟通 -> 读取上下文 -> 结构化跟进 -> 判断缺口与状态变化
-> 人工确认 -> 更新客户/商机/跟进 -> 创建任务 -> 追踪结果
```

核心价值指标是 **有效跟进闭环率**，而不是生成记录数量。一次沟通只有在结构化记录可信、
下一步明确、任务可追踪并产生后续状态时，才算形成有效闭环。

## 2. 产品边界

### 2.1 当前聚焦

- 用户：ToB 企业一线销售。
- 入口：飞书机器人私聊、交互卡片；Web 用于主动进入的复杂表单和查询。
- 事实源：客户、商机、跟进由 Base 或后续 CRM 适配器保存；任务由飞书 Task 保存；
  控制库保存会话、待确认动作、映射和审计。
- Agent 原则：大模型负责理解、抽取和建议；程序负责权限、规则、幂等、执行和记录。

### 2.2 明确不混淆的能力

语音转写、跟进结构化、提醒、知识问答、日报、风险评分和客户 360 视图可以分别成为
场景 Agent 的输入或能力，但不能只凭一个页面或一个模型提示就宣称完成。每个场景 Agent
必须有目标、触发、上下文、状态判断、工具调用、人工确认、失败转人工和结果追踪。

### 2.3 多 Agent 产品版图

产品由多个共享同一权限、上下文、确认、执行和审计底座的场景 Agent 组成：销售跟进、
商机推进、任务履约、商机停滞提醒、销售日报、团队 Review 和 Playbook 优化。当前销售跟进、
商机推进已有核心代码能力；任务履约 v1 已完成未完成任务的只读风险判断和 Web 产品面；
停滞提醒已完成只读扫描、安全门、运行前检查和 plan-only 计划；销售日报 v1 已完成只读
自动化实现并进入真实 Web/UI 验收；团队 Review v1 已完成只读 API 和 Web 产品面，Playbook
仍按阶段建设。
语音、会议纪要和文档解析作为后续输入型 Agent 扩展，不复制业务写入底座。

## 3. 完成度口径

所有阶段和需求统一使用以下四档；需求追踪矩阵必须同时记录自动化与 UI 证据。

| 状态 | 可宣称的事实 | 不可宣称的事实 |
| --- | --- | --- |
| `UI Verified` | 自动化与真实飞书/Web 端到端证据均存在 | 不代表所有相关扩展输入都完成 |
| `Automated Green / UI pending` | 测试、类型、Lint、构建已通过 | 不代表真实运行态和视觉交互已完成 |
| `Partial` | 已有可复用代码或局部流程 | 不代表闭环、权限或失败路径完整 |
| `Draft` | 已有规格或设计草案 | 不代表已经实现 |

历史验收只证明当时的版本和场景。代码或卡片契约发生变化后，必须用新运行态重新验收，
不能直接复用旧截图或旧日志作为完成证据。

## 5. 产品路线：一条主线，多种内部能力

### P0：跟进记录闭环基线

目标是把文字或会议纪要转成结构化跟进草稿，销售确认后写入客户、商机、跟进并创建任务。
P0 已形成历史真实闭环，但新版本变更仍必须保持它的回归通过。

### P1：销售跟进 Agent：持续执行闭环

P1 是当前最高优先级，完成条件不是“能生成卡片”，而是：

1. 识别客户、联系人和商机，并处理唯一匹配、无匹配和多匹配。
2. 读取近期跟进、商机状态、已有任务和权限上下文。
3. 判断状态变化、信息缺口和下一步行动，并保留来源证据。
4. 用可编辑卡片展示草稿和任务候选。
5. 用户一次确认后按版本执行：先保存跟进，再创建选中任务。
6. 对执行中、成功、部分失败、超时和修订提供唯一可追踪终态。
7. 所有写操作具备租户隔离、幂等、审计和失败恢复。

P1 不是一次性完成的“生成卡片”功能，而是同一个用户-facing Agent 的持续执行主线：

```text
用户输入客户沟通
-> 识别客户/商机/跟进/任务
-> 读取事实和历史上下文
-> 保存跟进计划
-> 持续监控状态、到期、逾期和信息缺口
-> 提出建议或生成动作草稿
-> 人工确认后执行写入/任务变更/外部沟通
-> 读取结果并继续跟进
```

P1 的切片顺序应先补“读”能力，再补更复杂的“判断”和“履约”：

```text
标准化查询端口 -> 历史上下文注入 -> 匹配/冲突/缺口判断
-> 版本化预览 -> 单次确认执行 -> 结果与修订
```

#### P1-CTX：跟进计划与业务上下文读取（自动化完成，UI 待验收）

在生成跟进草稿前，按租户和当前销售读取客户、联系人、商机、近期跟进和飞书任务，转换为
标准领域模型并附来源引用。查询只读，不产生 Base、Task 或控制库业务写入。

必须处理：唯一匹配、无匹配、多匹配、权限不足、跨租户、旧信息冲突和外部来源暂时不可用。
该切片完成后，Agent 才能基于事实判断状态变化和下一步，而不是只依赖用户本次输入。

#### P1-FULFILL：任务履约跟进

持续回收任务状态，识别即将到期、逾期、完成、变更和承诺未兑现，并把结果带回下一步建议。
普通内部提醒可按租户策略自动触发；更新任务、升级主管或对外沟通仍需确认。

当前 v1 已实现第一步：读取本人未完成飞书任务，按租户时区确定性分类逾期、今日到期、
三天内到期、未设期限和正常排期，并在 Web 提供只读建议；对 Agent 已确认且有精确
`taskGuid` 的承诺，依据详情/列表状态输出已完成、部分完成、仍未完成或待核实。
此外按负责人分页读取已完成任务，最多 10 页，只有可解析且大于 0 的 `completed_at` 才计入
已完成明细；零值按未完成/重新开放处理，覆盖范围明确标记为检索范围、部分或不可用。
现有检索契约仍不返回完整完成历史，因此全量完成率、没有任务承接时的兑现判断及主动提醒
不在本切片完成范围内。控制库已记录 Agent 自己观察到的精确任务状态事件，但这不是飞书全量
事件流；只有明确 `completed`/`reopened` 事件可恢复历史判断，跨任务替代关系必须由外部明确
提供 `relatedTaskGuid + relation: replaces`，且只能来自成功 Agent 动作结果；关系字段缺失、
冲突、自替代、读取失败、跨租户或跨销售均 fail closed，不允许模型按标题、时间或列表缺失猜测。
原任务仍可见时替代任务不得覆盖原任务结论；只有原任务不可见且替代关系通过全部校验时，才可
作为承接证据。

#### P1-PROGRESS：客户与商机推进（Goal v3 当前切片）

识别客户长期无回复、商机阶段停滞、关键角色/预算/竞争信息缺口和风险，给出带证据的推进建议。
修改商机阶段、金额、预计成交时间和任何对外承诺必须人工确认。

当前已完成“销售提交一次跟进”触发的判断快照：比较本次进展与匹配商机当前进展，展示事实、
Agent 判断、建议和待确认动作，并随草案版本保存。既有商机的赢单、丢单、关闭等状态变更
必须先由 Agent 唯一匹配并展示确认卡，确认后才写入；定时识别长期未更新不在本切片内。

### 后续能力：主动触发器（不是并列 Agent）

主动任务跟进是 P1 内部的触发与履约能力。完成 P1-CTX 后，先选择一个触发器做最小闭环，
推荐“商机超过 7 天没有更新”；随后再扩展任务即将到期、逾期、沟通与原任务不一致和承诺
未兑现等触发器。

每个触发器必须具备：规则扫描、是否需要提醒的判断、原因解释、建议动作、飞书提醒、
待确认任务、重复抑制和必要时升级主管。Agent 不得直接修改商机阶段或代表销售对外承诺。

### 后续能力：商机推进与风险洞察

商机推进是 P1-PROGRESS 的深化，不另起一个与销售跟进 Agent 冲突的用户-facing Agent。它需要完整商机历史、阶段
进入/退出标准、角色覆盖和 Playbook 资料；风险卡只能基于可定位证据，不得凭空预测。

### P4：管理 Review 能力

P4 面向主管，链路为“团队数据 -> 影响目标的问题 -> 具体商机 -> 管理动作 -> 主管确认 ->
任务分配与追踪”。它不是简单日报生成器。

### P5：Playbook 优化能力

P5 最后实施，依赖稳定的商机阶段、任务状态、赢单/丢单样本、Playbook 使用记录和效果评估。
输出先经管理员审核，再灰度发布，不能由模型直接改变全员打法。

## 6. 依赖关系与优先级

```text
客户/商机/任务/时间线事实
  -> 跟进结构化与确认
  -> 下一步与任务创建
  -> 任务状态与主动提醒
  -> 商机风险与推进建议
  -> 团队 Review
  -> Playbook 优化
```

因此后续不应同时启动多个用户-facing Agent。P1-CTX 的“读取上下文”、P1-FULFILL 的“任务
履约”和 P1-PROGRESS 的“状态判断”是同一主线的连续切片，也是管理 Review、知识问答和
Playbook 的共同基础，优先级高于语音、报告、RAG 和管理看板等扩展体验。

## 8. 统一 Agent 契约

每个新场景必须在规格中填写：目标、触发事件、可读数据、可调用工具、可自动执行动作、
必须人工确认的动作、停止/转人工条件和成功指标。高风险动作包括更新阶段、金额、预计成交
时间、通知主管和任何外部消息，必须人工确认。

程序负责权限、规则、状态、幂等、重试、审计和调度；模型负责意图、抽取、语义判断和建议；
RAG 只负责知识检索；事件/定时系统负责触发，不让模型自行伪造触发器。

## 9. 评测与发布门禁

每个切片必须通过：

1. 规格和需求编号已更新，且明确正常流、异常流、权限和副作用边界。
2. 先有 Red 场景，再以最小实现达到 Green。
3. 受影响单测、Agent 回归、Postgres 集成、三套 TypeScript、ESLint 和构建通过。
4. 真实飞书/Web 端到端证据已记录；未完成时只能标 `UI pending`。
5. `git diff --check` 通过，日志无未解释的运行错误。
6. 核心模块形成可回滚里程碑后，才允许执行仓库约定的 GitHub checkpoint。
