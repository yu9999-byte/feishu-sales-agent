# 执行反馈与结果修订：决策问答

状态：`已确认 / 2026-09-23`。规范以
`docs/specs/09-action-execution-feedback-sdd.md` 为准。

## 问：确认前要不要逐字段确认或连续点两次？

答：不要。客户、沟通、正文、下一步和待办选择位于一张完整表单中，销售修改完后一次提交。
服务端对整个版本做最终校验；校验失败才留在同一表单提示，不能先要求“检查修改”再点确认。

## 问：销售点击确认后应该看到什么？

答：同一卡立即变成“执行中，请等待”，按钮进入 loading/禁用状态。loading 动画由客户端能力
决定，持久执行中卡才是可靠状态。Base 和 Task 写入只能在回调返回后开始，避免用户看到原卡
不动，也避免快速终态被迟到的回调响应覆盖。

## 问：要不要逐步展示客户、商机、跟进和任务的每一步？

答：当前不需要。用户只需要明确系统已接单、不可重复提交，并最终拿到成功、失败或部分失败。
内部仍保存步骤级进度用于幂等恢复和审计，但不制造多张过程卡或滚动刷屏。

## 问：失败后怎样恢复？

答：失败卡保留表单和已完成外部 ID，提供“返回编辑”和“重试未完成步骤”。首次创建链重试时
跳过已完成步骤；更新链的 Base/Task patch 可幂等重复。不能无声停留在执行中。

## 问：成功后怎样编辑？

答：成功卡提供“编辑跟进”。点击后同一卡打开已保存结果的预填整表，销售一次提交修订。
系统更新原 Base 跟进；已有任务仍被选择时更新原 task GUID，不创建第二条跟进或任务。
取消选择已有任务只表示本次不更新它，不自动删除已经存在的任务。

## 问：执行中能不能真正撤销？

答：确认前可以取消；获取执行权后不承诺跨 Base 和 Task 的瞬时回滚，因为外部写入不是一个
事务。执行失败时展示部分完成并允许恢复；执行成功后通过可审计修订纠正结果，而不是偷偷删除。
