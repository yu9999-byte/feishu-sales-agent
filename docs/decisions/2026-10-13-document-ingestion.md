# 飞书文档录入跟进：决策问答

状态：`已确认并实现 / 自动化 Green / 真实文档与飞书 UI 待验收 / 2026-10-13`

本文件保留 B5 文档输入切片的产品与技术取舍。可执行契约以
[飞书文档跟进录入 SDD](../specs/40-document-ingestion-sdd.md) 为准。

## 问：销售发文档链接后，会直接写入跟进吗？

答：不会。文档只是输入来源，LangChain/LangGraph 仍负责判断是否为 `followup_capture`。
识别为写跟进后，系统读取正文、生成现有可编辑草案，并把一张确认卡发回原聊天。销售确认前
不写 Base、不创建任务。普通问答、内容生成和只分析文档继续走其他意图。

## 问：为什么必须使用销售自己的用户授权？

答：Docx 和 Wiki 是用户资源。机器人能访问不代表当前销售能访问，反过来也一样。生产读取
固定使用当前销售按租户/成员保存的 `user_access_token`；缺授权或 scope 时给本人授权入口，
不回退到 bot token，也不通过另一个用户代读。

## 问：为什么需要把 token 服务改成按场景校验 scope？

答：B4 曾把 token 获取硬编码为妙记权限，导致一个只授权 Docx 的合法 token 也会被妙记规则
错误拦截。现在调用方显式声明 required scopes：Docx 需要 `docx:document:readonly`，Wiki 还需
`wiki:node:read`，妙记继续使用自己的只读 scope。它们共用一份加密凭据，但权限判定互不
冒充。

## 问：Wiki 链接支持到什么程度？

答：首版先用当前用户身份解析 Wiki 节点，只有节点最终对象是 Docx 才继续读取。Sheet、Base、
画板、思维笔记、文件和其他类型明确提示暂不支持，不自动跳到其他 API，也不把对象名称当正文。

## 问：系统会读取图片、附件或嵌入表格吗？

答：不会。B5 的唯一事实正文是 Docx `raw_content`。标题和 revision 只作来源元数据；图片、
附件和嵌入对象不下钻。这样可以保证范围、权限、失败语义和证据定位清楚。后续若要支持附件
或表格，必须为对应资源单独定义用户授权、大小限制和证据契约。

## 问：长文档怎么处理？

答：送模正文上限为 120,000 个 UTF-16 code unit。系统优先保留完整首尾段落并显示省略标记；
单个段落过长时安全保留首尾，不能截断代理对，也不能悄悄超过上限。卡片来源快照记录已截断，
避免用户把部分读取误认为完整文档。

## 问：读取失败时会发生什么？

答：原聊天的“正在读取”消息会就地更新成授权、权限、类型不支持、空正文或可重试失败终态；
只有消息更新失败才补发。同一事件重投只读取一次。任何读取或抽取失败都不创建待确认动作，
更不写 Base/Task。

## 问：为什么本轮不直接做真实文档测试？

答：真实读取需要应用 scope、当前销售重新 OAuth 和明确的本人可读测试文档。本轮先完成规格、
失败测试、实现和隔离验证，不把替身网关结果冒充真实 UI 证据；真实读取和消息测试仍需单独
授权后执行。

## 实施结果

上述决策已进入生产工作流和自动化回归。额外边界包括：同一消息同时含妙记和文档时在任一
来源读取前拒绝；两个租户/成员使用各自 OAuth，且同一引用产生租户隔离的来源哈希；无标题但
有正文的 Docx 继续读取，并在草案中回退显示“飞书文档”。应用后台的 `wiki:node:read`、当前
销售重新 OAuth 和真实 Docx/Wiki 私聊验收尚未确认，本文件不把自动化结果写成真实完成。
