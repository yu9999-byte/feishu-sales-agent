# 对话入口与跟进质检重构：决策问答

状态：`产品决策已确认 / 2026-09-20`。本文件覆盖旧文档中“任意文本默认进入跟进抽取”
及“保存前把 0–100 分作为销售确认卡主信息”的交互口径。它不宣称所有能力已实现；
实施状态以需求追踪矩阵为准。

## 问：销售 Agent 是否应该能正常聊天？

答：是。飞书机器人首先是统一对话入口，收到消息后先结合当前会话识别意图，再进入
普通聊天、销售方法问答、内容生成、业务查询、跟进记录、任务操作或项目诊断。
“你好”“这单有什么风险”“帮我写封邮件”不能生成跟进草案，更不能写 Base/Task。
同一句可以包含多个意图，但每个外部写操作仍分别受权限、预览和确认约束。

## 问：什么情况下开始录入跟进？

答：销售明确说“记一条跟进/把刚才内容记成跟进”等，或主动打开“写跟进”表单，
才进入跟进录入。仅陈述“张总说预算下周批”而没有记录指令时，先问是要记录还是只分析，
不能猜测为写入授权。已有正在补字段的跟进会话可把销售回答并入该草案，但显式换话题、
取消、超时或跨聊天时不能继续吞掉其他问答；确认前仍无外部写入。

## 问：AI 质检为什么令人感觉像被考试？

答：旧卡把事实核对、记录完整度、商机风险与销售表现压成一个分数，并和保存确认捆绑。
预算/决策链可能只是本轮未涉及，不能因此判断销售本次沟通差。新交互拆成三种对象：

1. **保存前可用性检查**：只呈现“可以保存/需确认/建议补充”、明确缺口与证据问题。
   客户和有效沟通事实必须可靠；下一步不明确时可以说明“暂无下一步＋原因”，不建任务。
2. **保存后项目推进诊断**：结合历史的频率、阶段、竞品、情绪和任务等证据，只有新可行动
   风险、关键变化或主动请求时出现，不能拿单条记录完整度冒充项目健康度。
3. **按需销售辅导**：销售主动问“我这次谈得如何”时才评价沟通方法，给具体、可行动反馈，
   不默认作为每条记录的绩效标签。

原 0–100 质量快照若为兼容旧版本而保留，只能作为后台诊断/规则回归数据，不在机器人
默认确认卡上突出展示 A/B/C/D；后续评分模型须单独评审，不能作为自动绩效结论。

## 问：卡片和普通回复分别在什么时候用？

答：普通聊天、方法问答和授权范围内的查询直接文字回答；内容生成先给草稿而不保存；
不明确的意图用一句澄清。写跟进、建任务、改商机等外部副作用才给预览和确认卡。

2026-09-21 文案修订：澄清应自然承接为“收到。你希望我把它整理成一份待确认的跟进记录，
还是只分析它对商机的影响？”。不得把“我不会直接写入”等内部安全策略直接说给销售；
安全边界由确认门和状态机执行，而不是靠生硬文案解释。
跟进仍采用原聊天中的“草案/待办预览卡 → 结果卡 → 条件项目风险卡”，不是所有消息都
固定发卡。保存前卡以“我理解的事实”为主，提示少量必须确认项与非阻断建议，编辑后
更新同一卡；一次确认只覆盖该版本上清晰列出的写入与本人待办。

## 问：本轮如何分阶段实现与验收？

答：先做 B0 对话基座：普通聊天、销售方法问答、明确跟进意图与歧义澄清，并确保问答零
Base/Task 副作用；再做 B2 卡片可用性展示；客户/商机/任务查询、持久化多轮通用会话、
复杂多意图执行、RAG 与任务/商机写操作按后续切片实现。未接通的数据不能被模型编造成
“已查询”，未实现的动作需明确告知并提供可执行的现有入口。每切片先规格、Red 测试，
再最小实现、回归和真实飞书 UI 验收。

## 问：取消卡片和“今天上午通过飞书”应该怎样处理？

答：取消是业务终态，不是一次临时按钮反馈。系统先原子关闭 pending action，再使用保存的
飞书消息 ID patch 原卡为不可操作的“已取消”。patch 必须安排在卡片回调响应完成后执行；
真实 UI 已证明在回调内同步 patch 即使 OpenAPI 返回成功，也可能被飞书随后恢复的表单状态
覆盖。已取消动作上的重复取消因此同时承担幂等自愈作用。即使 patch 失败，也不能恢复待确认
或产生 Base/Task 副作用，失败需进入审计。

文本来源里的本次沟通方式、时间和主题属于跟进上下文，应由结构化提取契约显式输出并进入
保存前检查；“本次通过飞书沟通”和“下一步开飞书会议”不得混为同一字段。相对时间按租户
业务时区解析并输出显式 offset，用户界面只显示中文字段，不能泄漏
`communicationMethod` 一类实现名称。

旧决定 D-010..012 关于“原聊天确认、任务一次确认、项目风险条件性第三卡”继续有效；
本次仅覆盖“任何文本默认跟进”和“评分主导确认卡”的错误口径。

## 问：普通问答等待模型时，要不要展示“思考过程”？

答：要让销售立即知道消息已被 Agent 接收并正在处理，但不能把模型的隐藏推理过程或
未经验证的内部步骤当作事实展示。普通问答先在原聊天发“正在组织回答…”，随后编辑
同一条文本为自然语言答案；模型失败则改为明确错误，编辑失败才补发终态。这样保留
“聊天以文本回答、写入才用确认卡”的产品边界，也不让等待提示永久占据两条消息。

## 问：14:35 的“你可以帮助我做什么”为何没有回复？

答：飞书事件配置仍指向临时公网隧道，但该隧道已退出，旧入口返回 404；本地 Agent
仍返回 200。因此消息未到 Agent，不能归因于意图识别。需恢复公网通路并更新回调，
再用真实飞书私聊复验。临时隧道只是联调设施，后续正式运行须稳定域名、托管和监控。

## 问：问完“记录还是分析”后，销售说“写跟进呀”为什么不能再问一遍？

答：这不是一个新的独立命令，而是对上一轮澄清的回答。Agent 必须保存一个有 TTL 的短期
“等待记录/分析选择”会话，并以租户、销售和原聊天三重约束读取。选择记录时只把上一条
客户沟通原文送入提取器，不能把“写跟进呀”污染进业务事实；选择分析时分析上一条原文并
关闭会话，保持 Base/Task 零副作用。跨聊天、跨用户、跨租户、超时、取消或明显换话题均
不承接。没有有效上文时，“写跟进呀”仍打开空白录入表单。

## 问：原文中的下一步时间已经过去，还能保存跟进和创建待办吗？

答：真实沟通记录仍可保存，因为历史事实不应因计划过期而丢失；但过期时间不能生成默认
勾选的可执行待办。任务候选应显示“执行时间已过期，请修改”，保持禁用，销售改为未来时间
并重新检查后才能选择创建。这将“记录事实”和“授权未来动作”分开，避免制造一条创建即
逾期的任务。
