# 跟进、质检与待办：决策问答

状态：`已确认；文本两卡闭环已 UI Verified / 2026-09-20`。适用于 Goal v3 的目标体验；
不追溯宣称 P0 旧卡片已经实现。
本文件保存讨论过程和被覆盖的旧口径。规范与验收以 `docs/specs/` 中同步修订的条款为准。

## 2026-09-21 确认按钮与成功回执修订

问：销售在卡片中改了字段后点“确认保存”，是否还要再点一次？

答：不需要。“检查修改”表示只保存当前编辑、重算检查和待办预览，不写入；
“确认保存”表示用卡片当前值做最后检查并直接登记。旧实现把“回调值有变化”
优先于按钮意图，导致确认被退化为只检查并要求二次点击，该口径被本决策覆盖。

问：登记成功后，销售如何确认结果并查看记录？

答：原草案卡就地更新为唯一一张绿色“跟进登记成功”卡，不再额外发送内容相同的结果卡。
该卡必须保存并使用 Base API 返回的跟进 `record_url`，提供“查看跟进记录”；如创建了待办，
另提供“打开飞书任务”。原卡更新失败时才补发一张结果卡，并分别记录 patch 或补发审计。

问：为什么旧版一次确认会看到两张“跟进登记成功”？

答：旧版既 patch 原草案卡为完整成功卡，又新增完整结果卡；控制库虽然只有一次执行，界面却
重复表达同一个结果。D-022 明确覆盖该设计，一个业务动作只有一个主结果凭证。

## 问：销售从哪里收到反馈？需要跳 Web 确认页吗？

答：销售从飞书机器人聊天提交文本、语音、妙记或飞书文档链接，就在**原聊天**收到草案、
质检、确认和执行结果。Web 可用于复杂浏览和主动打开的表单，但不是机器人输入的强制确认门。
旧 Phase B 文档中“编辑可以打开 Web 编辑页”只能是销售自愿选择的辅助入口，不能代替聊天确认。

## 问：跟进、AI 质检和待办是三件事，就固定发三张卡吗？

答：不是。三种跟进卡按事件出现：

1. **草案＋保存前实时质检卡**：AI 生成后发到原聊天；销售在卡中补充/修改、重新检查，
   并预览从“下一步计划”识别的本人待办。编辑后更新同一张卡，不反复发送新卡。
2. **执行结果＋已创建任务卡**：销售确认后，先写客户、商机和跟进，再自动创建已预览、
   已授权的飞书任务；成功、无任务及部分失败分别显示真实执行结果和入口。
3. **项目推进质检卡**：保存后结合历史数据分析项目健康；只有出现新的可行动风险、
   关键变化或销售主动要求分析时单独推送。分数可在商机详情查看，不靠每次发卡展示。

一次完整且无新风险的跟进通常收到前两张；没有合格任务则结果卡说明未创建任务；
高风险可能收到第三张。跨角色推送、日报周报、任务提醒是独立事件卡，不计入这个固定序列。

## 问：质检究竟在保存前还是保存后？

答：两者对象不同。保存前检查这条跟进的字段、下一步时间/方式/参与人、证据和风险提示，
销售可以修改后重新检查；保存后项目质检结合跟进频率、阶段停留、情绪、竞品和任务履约，
给出有证据的项目健康度、风险和建议。跟进内容质量分不等于项目健康度分，均不能单独用于
惩罚性绩效结论。Web 表单可在字段变化时即时检查；飞书卡片在提交/点击“检查”后更新，
不承诺每个按键实时刷新。

## 问：下一步任务是自动建，还是先让销售确认？

答：**一次确认覆盖两个明确列出的写操作**。在草案卡展示最终跟进版本及任务预览（标题、
截止时间、本人负责人、关联客户/商机）；销售点击“确认保存并创建所示待办”后，系统先
持久化业务事实，再只对选中的、可执行的本人任务创建飞书任务。没有明确下一步、时间或
执行人时，追问或请销售明确“暂无下一步＋原因”，不得编造任务；无可执行任务时按钮文案
变为“确认保存（不创建待办）”。涉及他人负责人必须单独检查分配权限并明确确认，
不得由这个本人任务默认授权推断许可。

任务候选可以在保存前抽取用于预览，但飞书任务只在跟进写入成功后创建。这保留了
“保存后自动创建”体验，不产生未经销售见过的任务。多个任务在同一卡中集中预览并选择；
结果卡中分别列出创建成功、未选择和创建失败项。重复回调、部分失败续跑不得重复写入。

## 问：四个“必填”与没有下一步的场景怎么兼容？

答：客户、联系人、沟通方式、下一步计划都列为完整度检查项，缺失时逐项提示，不用 AI
猜测填充。销售可明确标注“未知联系人”或“暂无下一步＋原因”，保留可追溯的未知状态；
这不等于获得完整度满分，也不生成任务。客户身份或有效沟通正文无法确定时不允许确认写入。
下一步三要素按时间、地点/方式、参与人检查；纯线上事项不强制物理地点，但要说明方式。

## 问：新需求、风险、里程碑、竞品出现，就自动广播吗？

答：普通保存结果只给销售本人。跨角色通知必须在销售确认的事实基础上，按租户开启的策略、
角色和资源级权限、有效收件人映射、证据和去重规则执行。支持请求的对象、团队群里程碑
需要销售明确确认；竞品提及默认先给本人，市场/主管可配置且有权访问才接收。不能把
未确认草案、客户敏感原文或无权查看的客户信息推给其他人。

## 问：任务状态、提醒和报告会怎样运行？

答：AI 只能**建议**“已完成、部分完成、未完成或已变更”，给销售看证据后由本人确认
实际状态变更；不能先自动改完再要求追认。到期前一天、当天、逾期提醒按租户时区、
免打扰和去重策略，任务完成/变更/暂缓后停止旧提醒。日报周报仅用已确认数据，定时报告
保存快照和版本，和单次录入的卡片序列分离。没有 Playbook、历史样本或可信证据时，
建议明确降级，不编造案例或精确健康分。

## 2026-09-20 条件项目质检切片更新

问：条件项目质检卡现在什么情况下会发？

答：本切片只在保存成功、结果卡已发送后，命中本次已确认原文中可定位的明确负向/停止推进、
竞品介入、售前/产品支持请求或明确逾期行动时追加发送。仅“预算未知”或“决策链未知”不追加风险卡。
风险卡逐条展示证据与建议，并写明“样本不足，暂不生成项目健康度评分”；它不复用保存前跟进质量分。

问：风险卡发送失败会不会回滚跟进和待办？

答：不会。执行顺序是 Base/Task 成功、原聊天结果卡、条件风险卡；风险卡是通知副作用，发送失败只追加
失败审计并保留已成功的 Base/Task/结果，不把已完成业务动作改成失败。

本切片历史自动化证据：19 个测试文件、107 项测试通过；加入 B0 对话入口与卡片呈现修订后，
当前全量基线为 20 个测试文件、117 项测试。普通文本场景因预算/决策链未知不构成
发卡条件，真实 UI 正确地只出现草案/质检卡和结果卡。带明确风险证据的第三卡仍待单独 UI 验收。

## 2026-09-20 真实 UI 验收后的补充问答

问：执行成功后，原草案卡为什么不能继续保留确认按钮？

答：原卡必须持久化为不可操作的完成态。只返回回调同步卡或依赖短期 callback token，可能被
飞书的回调响应覆盖，出现“数据库已成功、原卡仍显示 v3 按钮”的错觉。最终决定是保存卡片
`message_id`，在执行终态落库后调用消息 patch 更新原卡。旧版曾把独立结果卡作为第二张凭证，
但真实使用证明会造成重复结果；该口径已被 D-022 覆盖，仅在原卡 patch 失败时补发。
重复点击继续由动作状态机兜底，不得重复写 Base 或创建任务。

问：飞书日期控件应该接收 UTC 还是本地业务时间？

答：内部继续保存 ISO 时刻；构造 `picker_datetime.initial_datetime` 时，先按租户业务时区
（当前为 `Asia/Shanghai`）转换为本地年月日时分。真实 UI 已核对 2026-09-22 14:00，不能
把 UTC 字符串直接截断后交给控件。

问：这次文本闭环的真实证据是什么？

答：同一机器人聊天完成录入、补字段、AI 草案、v2/v3 再质检和一次确认；Base 中客户、商机、
跟进分别为 `recvvKXMCHeUK2`、`recvvKXNoHC16k`、`recvvKXO88qZRX`；飞书任务为
`66bbc267-e50c-476e-a01c-9ffd100fbe5c`（`t142596`），任务 UI 显示负责人李胜彬、截止
2026-09-22 14:00、状态未完成。审计仅一次确认和一次成功；原卡与独立结果卡都显示完成是
历史版本证据，不再代表现行单成功卡体验。

## 被覆盖的旧口径与执行检查

| 旧口径 | 新决定 | 修订位置 |
| --- | --- | --- |
| P0 只有“确认并执行/取消”；修正靠重新发文本 | Goal v3 在原聊天卡中编辑、再质检、一次确认 | `agent-experience.md`、Phase B |
| 从机器人卡片跳 Web 编辑是默认路线 | Web 是可选辅助，不是确认必经页 | Phase B、信息架构 |
| 无下一步仍直接保存且无提示 | 必须提示；允许显式“暂无下一步＋原因”，不建任务 | 需求、Phase B |
| 保存后再发待办确认卡，同时宣称自动创建 | 保存前预览并一次确认；保存后自动建已批准任务 | 业务架构、Phase B |
| AI 自动改任务完成状态后请销售确认 | 先给判断，确认后才改状态 | 产品需求、Phase B |
| 新需求/竞品/里程碑一律扩散 | 有证据、权限、策略和对应确认才推送 | 角色权限、Phase B |

实施按 SDD/TDD 分切片：先卡片内编辑/再质检/任务预览和一次确认，再输入适配器，
再做策略推送、任务回收与提醒、日报、完整历史项目质检和团队报告。每切片先保存 Red/Green、
回归，再用真实飞书聊天 UI 和 Base/Task/审计对账；自动化通过不能代替 UI 验收。
