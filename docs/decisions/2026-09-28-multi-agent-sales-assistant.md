# 多 Agent 销售助手产品方向

日期：2026-09-28  
状态：`Confirmed / product direction`

## 决策

本项目不是只有一个销售跟进 Agent，而是建设一个面向 ToB 销售的多 Agent、
多场景销售助手。销售跟进 Agent 是当前最完整的首个场景，不代表产品边界。

各场景 Agent 共享统一底座：用户身份与权限、客户/商机/跟进/任务上下文、
LangGraph 会话、确认卡、执行状态、幂等、重试、审计和飞书/Web 入口。
每个 Agent 仍必须有明确目标、触发条件、可读数据、可调用工具、确认边界、
失败转人工条件和可验证结果。

## Agent 版图

| Agent | 产品职责 | 当前状态 |
| --- | --- | --- |
| 销售跟进 Agent | 把客户沟通转成可确认、可执行、可追踪的跟进闭环 | 核心已实现，真实 UI 终态待验收 |
| 商机推进 Agent | 判断商机进展、缺口、风险和状态变更 | 核心已实现，受控状态更新已验收 |
| 任务履约 Agent | 创建、更新、追踪销售任务并反馈结果 | v1 已实现未完成任务风险判断和 Web 产品面；完成历史、承诺核对、提醒与升级待实现 |
| 商机停滞提醒 Agent | 发现长期未更新商机并提醒销售 | 扫描已实现，主动闭环未完成 |
| 销售日报 Agent | 汇总个人跟进、任务、商机变化并给出行动建议 | v1 只读 API/Web 已实现，自动化完成，真实 UI 待验收 |
| 团队 Review Agent | 面向主管聚合团队风险并推动管理动作 | v1 只读 API/Web 已实现，真实 UI 与管理动作待验收 |
| Playbook 优化 Agent | 基于赢单/丢单样本提炼和迭代销售打法 | 规划阶段，依赖更多稳定数据 |

语音、会议纪要、文档解析等属于输入型场景 Agent，后续作为统一销售助手的扩展入口，
不是与上述业务 Agent 重复的独立数据底座。

## 建设顺序

1. 保持销售跟进 Agent 为首个可用主线，同时补齐真实 UI 终态验收。
2. 对销售日报 Agent v1 做真实 Web/UI 验收；确认只读数据和任务读取运行态后，再决定推送策略。
3. 将商机停滞扫描补成默认关闭的主动闭环：定时触发、持久去重、提醒和确认。
4. 实现团队 Review Agent，形成主管视角的风险聚合与管理动作。
5. 再建设语音/会议/文档输入 Agent，最后推进 Playbook 优化 Agent。

## 边界

多 Agent 不等于多个机器人各自复制一套权限和写入逻辑。高风险动作仍必须人工确认；
Agent 负责理解、判断和建议，程序负责权限、规则、状态、幂等、执行和审计。
未完成的 Agent 只能标记为 `Draft` 或 `Partial`，不能因为已有路由或内部服务就宣称可用。
