# GitHub 自动检查点

本项目通过安全快照发布器维护 `github/main`。发布器不会切换当前分支，也不会修改用户的
工作区或暂存区；它使用临时 Git 索引收集全部未忽略文件，以最新 `github/main` 为父提交
创建增量检查点，并仅执行普通快进推送。

## 触发方式

核心模块或阶段达到稳定验收点后立即执行：

```text
npm run github:publish -- --kind milestone --summary "完成客户模块闭环"
```

每日 Codex 自动化在北京时间 21:30 复核一次。它只在改动形成稳定阶段时使用 `daily`
检查点补漏；无变化、仍在开发中或仅有琐碎修改时不发布。

执行真实发布前可运行完整预检：

```text
npm run github:publish:check -- --kind milestone --summary "完成客户模块闭环"
```

## 阶段判定

以下情况适合创建检查点：

- 一个领域模块或跨层功能已经闭环，相关验收标准和测试均通过。
- 一个项目阶段已完成，其状态文档、实现和验证证据保持一致。
- 形成了可独立回滚的稳定架构节点，继续开发将进入下一阶段。

以下情况不发布：

- 仍是脚手架、占位实现、调试中间态或失败状态。
- 只有格式、拼写或生成文件变化，尚未形成有意义的项目进展。
- 无法准确说明完成结果，或相关验收与测试尚未通过。

## 安全门

发布器会在提交前：

1. 获取最新 `github/main`，并拒绝向 `origin` 发布。
2. 使用临时索引生成快照，不读取或覆盖用户暂存区。
3. 拒绝 `.env`、私钥、凭据文件、运行时目录、生成目录和超过 25 MiB 的文件。
4. 对文本内容扫描已知令牌格式和高熵凭据赋值，只报告位置而不输出密钥内容。
5. 运行 `npm run lint`、发布器隔离测试和完整 Agent 测试。
6. 创建以远端最新提交为父节点的提交，并执行非强制推送。
7. 回读远端分支，确认提交哈希一致。

任一门禁失败时不创建远端提交。远端在检查后发生并发更新时，普通推送会失败，发布器不会
自动覆盖别人的提交。

## 提交格式

里程碑提交使用 `checkpoint(milestone): <summary>`；每日补漏使用
`chore(snapshot): <summary>`。提交正文记录源分支和源 `HEAD`，便于追溯，但 GitHub 历史
始终以 `github/main` 为主线。
